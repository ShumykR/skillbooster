# Каталог практичних завдань і production-кейсів

Формат кожного завдання: **що робимо** → **за чим перевіряємо** (автотест / скрипт / ручна перевірка).
Рівні: 🟢 база · 🟡 середній · 🔴 просунутий.
Завдання з позначкою 🤖 використовують LLM і працюють через налаштовуваний проксі (див. розділ «AI-проксі»).

## A. Python і FastAPI у production

1. 🟢 **Структура проєкту:** розкласти застосунок на шари (router → service → repository), конфіг через pydantic-settings. *Перевірка:* тест імпортів і залежностей між шарами. *Патерн:* Layered architecture
2. 🟡 **Async під навантаженням:** ендпоінт, що ходить у 3 зовнішні сервіси паралельно (`asyncio.gather`), з таймаутами та обмеженням паралелізму (semaphore). *Перевірка:* тест із повільним мок-сервером, час відповіді < порогу.
3. 🟡 **Блокуючий код в async:** знайти й виправити синхронний виклик, що вішає event loop (`run_in_executor` / `to_thread`). *Перевірка:* тест вимірює затримку паралельних запитів.
4. 🟡 **Dependency injection та тестування:** переписати код так, щоб БД і зовнішні API підмінювались у тестах (`dependency_overrides`). *Перевірка:* набір тестів без реальної мережі.
5. 🟡 **Валідація та контракти:** строгі pydantic-моделі, версіонування API (`/v1`, `/v2`), зворотна сумісність. *Перевірка:* контрактні тести старих клієнтів. *CWE:* ?20
6. 🟡 **Пагінація:** cursor-based замість offset на великій таблиці. *Перевірка:* тест стабільності при вставках під час обходу.
7. 🟡 **Централізована обробка помилок:** єдиний формат помилок (RFC 7807), коректні статуси, відсутність витоку stack trace. *Перевірка:* перебір негативних сценаріїв. *CWE:* 209, 248, 550, 756, ~703, ~200, ~20
8. 🟡 **Background tasks vs черга:** коли `BackgroundTasks` достатньо, а коли потрібен Celery/ARQ/RQ. *Тип:* практика *Кроки:* поставити Redis (docker compose) і ARQ або RQ | зробити `POST /signup`, що відправляє лист через `BackgroundTasks` з імітацією SMTP (пауза + випадковий збій) | вбити процес API одразу після відповіді й переконатися, що лист загубився без сліду | перенести відправку в чергу з воркером: ретраї з наростаючою паузою, ліміт спроб, dead letter | зробити задачу ідемпотентною (ключ повідомлення), щоб повторна доставка не слала два листи *Готово:* після `kill -9` API лист усе одно доходить через воркер | збій SMTP дає 3 ретраї з наростаючою паузою, потім запис у dead letter або лог | повторна доставка тієї самої задачі не відправляє другий лист | у README три речення: коли `BackgroundTasks` достатньо, а коли потрібна черга *Перевірка:* переписати відправку листа в чергу.
9. 🔴 **Graceful shutdown:** не губити запити при деплої, обробка SIGTERM, lifespan-події. *Тип:* практика *Кроки:* зробити ендпоінт `/slow` (5 с) і `lifespan`, що закриває пул з'єднань та логує кроки | запустити `uvicorn`, у іншому терміналі надіслати 20 паралельних запитів до `/slow` і одразу `SIGTERM` процесу | налаштувати `--timeout-graceful-shutdown`, переконатися, що поточні запити добігають | у Docker використати exec-форму `CMD [...]` (не shell-форму), щоб сигнал дійшов до процесу, і `stop_grace_period` | прибрати з readiness-проби інстанс перед зупинкою (у K8s: `preStop` + `terminationGracePeriodSeconds`) *Готово:* під час `SIGTERM` усі запити, що вже почались, завершуються кодом 200, обірваних 0 | у логах видно послідовність: отримали SIGTERM, перестали приймати, дочекались, закрили пул | `docker stop` завершується швидше за `stop_grace_period` з кодом виходу 0, а не 137 | скрипт навантаження лежить у репозиторії й відтворює перевірку однією командою *Перевірка:* скрипт шле запити під час рестарту, 0 обірваних.
10. 🔴 **Профілювання:** знайти вузьке місце (cProfile / py-spy), прискорити ендпоінт у 5 разів. *Тип:* практика *Кроки:* взяти ендпоінт зі списком записів (з N+1 або вкладеним циклом) і зафіксувати базу: `hey`/`wrk`/`locust`, rps і p95 | зняти профіль: `python -m cProfile -o out.prof` і `snakeviz`, або `py-spy record -o flame.svg --pid` | знайти топ-3 функції за кумулятивним часом | виправляти по одній проблемі й після кожної повторювати вимір з тим самим навантаженням | зберегти звіт або flamegraph до і після *Готово:* є вимірювання до/після з однаковим навантаженням (rps і p95) | прискорення не менше ніж у 5 разів або пояснення, чому менше | профіль або flamegraph до і після збережені | для кожної зміни є рядок «що показав профіль, що зробили, на скільки швидше» *Перевірка:* бенчмарк до/після.
11. 🔴 **Memory leak:** знайти витік (tracemalloc / memray) у навмисно зламаному сервісі. *Перевірка:* пам'ять не росте за N запитів.
12. 🟡 **Типізація та лінтинг:** mypy strict, ruff, pre-commit. *Тип:* практика *Кроки:* додати до `pyproject.toml` налаштування `ruff` (lint і format) та `mypy --strict` | виправити помилки в проєкті по модулях: спершу нові, `# type: ignore[код]` лише з коментарем-причиною | додати `.pre-commit-config.yaml` з ruff, ruff-format і mypy | додати крок у CI, що запускає ті самі перевірки *Готово:* `ruff check .` і `ruff format --check .` без зауважень | `mypy --strict` чистий (або винятки в `overrides` з причиною) | `pre-commit run --all-files` зелений, а коміт із помилкою типів блокується | CI падає на навмисно доданій помилці типів і зеленіє після виправлення *Перевірка:* CI проходить.
13. 🟡 **Завантаження файлів:** потокове завантаження великих файлів, ліміти розміру, перевірка типу, presigned URL до S3 замість проходу через бекенд. *Перевірка:* тест із файлом 500 МБ та обмеженою пам'яттю. *CWE:* ?434
14. 🟡 **Експорт великих даних:** streaming CSV/NDJSON-відповідь без завантаження всього в пам'ять. *Перевірка:* вимір пікової пам'яті.
15. 🟡 **WebSocket / SSE:** живі сповіщення, реконнект, backpressure. *Перевірка:* тест із клієнтом, що відвалюється.
16. 🟡 **Мультитенантність:** ізоляція даних між клієнтами (tenant_id у кожному запиті, row-level security у Postgres). *Перевірка:* тест, що тенант A не бачить дані B. *CWE:* 639, 862, ~89 *Патерн:* Repository
17. 🟡 **Feature flags:** поступове розгортання функцій на відсоток користувачів. *Перевірка:* розподіл у допуску.
18. 🟡 **i18n та часові пояси:** зберігати UTC, віддавати локально, ловити DST-баги. *Перевірка:* набір дат на межах переходу часу.
19. 🟡 **Гроші:** `Decimal` замість float, округлення, мультивалютність. *Перевірка:* тести на копійчані розбіжності.

## B. Бази даних у production

20. 🟢 **Нормалізація:** з «плоскої» таблиці зробити схему до 3NF. *Перевірка:* скрипт порівнює залежності.
21. 🟡 **Міграції без простою:** додати NOT NULL колонку до великої таблиці в кілька кроків (expand → backfill → contract) на Alembic. *Перевірка:* тест не блокує запису під час міграції.
22. 🟡 **N+1 запит:** знайти й виправити в SQLAlchemy (`selectinload`/`joinedload`). *Перевірка:* лічильник запитів ≤ N.
23. 🟡 **Індекси:** композитні, часткові, покриваючі; прибрати Seq Scan. *Перевірка:* аналіз `EXPLAIN` у тесті.
24. 🔴 **Повільний запит:** оптимізувати запит із 8 секунд до мілісекунд: переписати `WHERE` без функцій над колонкою й додати індекс. *Перевірка:* автотести (кроки SQLite VM і план запиту замість секунд).
25. 🟡 **Транзакції та ізоляція:** відтворити lost update, dirty/non-repeatable read, виправити через `SELECT ... FOR UPDATE` або рівень ізоляції. *Перевірка:* паралельний тест. *CWE:* ~362
26. 🔴 **Deadlock:** відтворити та виправити порядком блокувань. *Перевірка:* 100 паралельних транзакцій без помилок. *CWE:* 362
27. 🟡 **Optimistic locking:** поле version, обробка конфліктів. *Перевірка:* два одночасні оновлення. *CWE:* 362
28. 🟡 **Idempotency key для платежів:** повторний запит не створює другого списання. *Перевірка:* дубль-запити, ретраї, гонка. *CWE:* 362 *Патерн:* Idempotent Receiver
29. 🔴 **Outbox pattern:** гарантована доставка події разом із записом у БД. *Перевірка:* вбити процес між записом і публікацією, подія не губиться. *Патерн:* Transactional Outbox
30. 🟡 **Soft delete та аудит:** журнал змін, хто й коли змінив. *Перевірка:* відновлення запису. *CWE:* ~223, ~778, ~460 *Патерн:* Repository
31. 🟡 **Connection pooling:** розмір пулу, PgBouncer, «too many connections». *Перевірка:* навантажувальний тест. *CWE:* ~460, 770 *Патерн:* Object Pool
32. 🔴 **Партиціонування:** великої таблиці подій за часом, видалення старих партицій. *Перевірка:* план запиту торкається однієї партиції.
33. 🟡 **Резервні копії та відновлення:** pg_dump/PITR, повне відновлення на чистий інстанс. *Перевірка:* порівняння контрольних сум даних.
34. 🟡 **Read replica:** розвести читання та запис, врахувати replication lag. *Перевірка:* тест «прочитав свій запис». *Патерн:* Read/Write Splitting
35. 🟡 **Redis кеш:** cache-aside, TTL, інвалідація при оновленні. *Перевірка:* лічильник звернень до БД. *CWE:* ~636, ~703 *Патерн:* Cache-Aside
36. 🔴 **Cache stampede:** захист від одночасного перерахунку (lock, jitter, stale-while-revalidate). *Перевірка:* 1000 паралельних запитів на протухлий ключ → 1 звернення до БД. *Патерн:* Single-flight
37. 🟡 **Rate limiter:** token bucket / sliding window на Redis. *Перевірка:* точність ліміту під конкуренцією. *CWE:* 770, 799 *Патерн:* Token Bucket
38. 🟡 **Повнотекстовий пошук:** Postgres FTS (`tsvector`, GIN) vs Elasticsearch/OpenSearch. *Тип:* практика *Кроки:* поставити Postgres у Docker і завантажити 100–200 текстів (README своїх проєктів, статті, нотатки) у таблицю `docs(title, body)` | скласти 15 запитів і для кожного записати, які документи мають бути знайдені (еталон) | додати `tsvector` як generated-колонку (title з вагою A, body з вагою B) і GIN-індекс, шукати через `websearch_to_tsquery` та `ts_rank_cd` | порівняти конфігурації `simple` та `english` (для українського тексту `simple` + `unaccent`) | порахувати precision@3 для кожної конфігурації | `EXPLAIN ANALYZE` до і після GIN: Seq Scan проти Bitmap Index Scan *Готово:* для 15 запитів порахована precision@3 для двох конфігурацій і видно, яка краща та чому | запит із синонімом або помилкою в слові показує межу FTS (там потрібен trigram, векторний пошук або гібрид) | `EXPLAIN ANALYZE` підтверджує використання GIN | є 3–5 рядків висновку: коли досить Postgres FTS, а коли потрібен Elasticsearch/OpenSearch *Перевірка:* релевантність на еталонному наборі.
39. 🔴 **Векторний пошук:** pgvector, індекси HNSW/IVFFlat, компроміс швидкість/точність. *Перевірка:* recall@k.

## C. API-дизайн і інтеграції

40. 🟢 **REST-рев'ю:** виправити «поганий» API (дієслова в URL, неправильні статуси). *Перевірка:* лінтер OpenAPI (Spectral).
41. 🟡 **Вебхуки:** приймати з перевіркою HMAC-підпису, захист від replay, ідемпотентна обробка, швидка відповідь 200 + черга. *Перевірка:* підроблені й повторні події. *CWE:* 347, 345, 294
42. 🟡 **Вебхуки, що відправляємо:** retry з експоненційним backoff, підпис, журнал доставки. *Перевірка:* нестабільний мок-приймач.
43. 🟡 **Клієнт до чужого API:** retries, таймаути, circuit breaker, rate-limit 429 з `Retry-After`. *Перевірка:* мок, що падає. *CWE:* ~703 *Патерн:* Retry, Circuit Breaker
44. 🟡 **Інтеграція платежів (Stripe-подібна, sandbox):** checkout, вебхук, статуси, повернення коштів. *Тип:* практика *Кроки:* створити безкоштовний акаунт Stripe в test mode і покласти ключі в `.env` (не в git) | зробити `POST /checkout`, що створює Checkout Session і віддає URL | додати `POST /webhooks/stripe` з перевіркою підпису (локально `stripe listen --forward-to`) | обробляти `checkout.session.completed`: замовлення стає `paid` лише тут, не після редіректу користувача | зберігати `event.id`, щоб повторна доставка не дублювала дію | зробити повернення коштів через API і статус `refunded` | перевірити тестовими картками: успіх `4242 4242 4242 4242`, відмова `4000 0000 0000 0002` *Готово:* оплата тестовою карткою переводить замовлення в `paid` тільки після вебхука | повторна доставка того самого `event.id` нічого не змінює вдруге | відхилена картка лишає замовлення неоплаченим із зрозумілою причиною | повернення коштів видно і в твоєму статусі, і в панелі Stripe | у репозиторії немає ключів Stripe *Перевірка:* тестовий режим.
45. 🟡 **OAuth2 «Увійти через Google/GitHub»:** authorization code + PKCE. *Перевірка:* e2e з мок-провайдером. *CWE:* ?346, ?287
46. 🟡 **GraphQL vs REST:** реалізувати один і той самий API двома способами, порівняти N+1 та DataLoader. *Перевірка:* тести обох.
47. 🔴 **gRPC:** сервіс із proto-контрактом, streaming, сумісність версій. *Тип:* практика *Кроки:* описати `.proto`: сервіс із unary-методом і server streaming | згенерувати код (`grpcio-tools`) і додати команду генерації в `Makefile` | реалізувати сервер (`grpc.aio`) і клієнт | повертати помилки через статус-коди (`NOT_FOUND`, `INVALID_ARGUMENT`), а не рядками | виставити deadline на клієнті й перевірити `DEADLINE_EXCEEDED` на повільному сервері | додати нове поле з НОВИМ номером, а видалене позначити `reserved` *Готово:* клієнт викликає unary-метод і читає потік відповідей | неправильний запит дає `INVALID_ARGUMENT`, відсутній ресурс `NOT_FOUND` | повільний сервер дає `DEADLINE_EXCEEDED` на клієнті | клієнт, зібраний зі СТАРОГО `.proto`, працює з новим сервером | згенерований код відтворюється однією командою *Перевірка:* згенеровані клієнти.
48. 🟡 **Генерація SDK з OpenAPI:** автоматично зібрати клієнт і опублікувати. *Тип:* практика *Кроки:* зберегти `openapi.json` свого FastAPI-сервісу в репозиторії | згенерувати Python-клієнт (`openapi-python-client` або `openapi-generator`) | додати в CI крок, що пересобирає клієнт і падає, якщо `git diff` непорожній (контракт змінився, клієнт ні) | налаштувати версію пакета за semver | опублікувати в TestPyPI через GitHub Actions з Trusted Publishing (без токенів у секретах) | написати тест, що клієнт працює проти запущеного сервісу *Готово:* клієнт встановлюється з TestPyPI і викликає хоча б один ендпоінт | CI падає, коли `openapi.json` змінено без перегенерації клієнта | після зміни контракту версія пакета піднята за semver | у згенерованому коді немає ручних правок: кастомізація лише обгорткою чи шаблонами *Перевірка:* CI.
49. 🟡 **Надсилання листів і сповіщень:** шаблони, черга, відписка, bounce-обробка. *Перевірка:* мок SMTP.

## E. Linux, мережа, Docker

63. 🟢 **Командний рядок:** grep/awk/sed/find/xargs, пайпи на реальних логах. *Тип:* практика *Кроки:* пройти на OverTheWire Bandit рівні 0–12 (SSH-гра, безкоштовно) або аналог на KodeKloud | для кожного рівня, де використано `grep`, `awk`, `sed`, `find`, `xargs` чи пайпи, записати команду й пояснення, чому саме вона | взяти реальний лог (nginx access.log або свій uvicorn) і порахувати: топ-10 IP, розподіл статус-кодів, найповільніші 5 URL, помилки 5xx за хвилину | виконати те саме з `awk` і з Python, порівняти по читабельності *Готово:* пройдено щонайменше 12 рівнів Bandit | є шпаргалка з 10+ команд, кожна з прикладом на реальних даних | топ-10 IP, розподіл статусів, повільні URL і 5xx за хвилину отримано одним пайпом кожен | можеш пояснити різницю між `find -exec` і `find | xargs` та між `grep -E` і `grep -P` *Перевірка:* KodeKloud / Bandit.

125. 🟡 **Code review:** знайти 10 проблем у навмисно поганому PR. *Тип:* документ *Кроки:* написати (або попросити AI згенерувати) PR на 150–200 рядків FastAPI-ендпоінта з навмисно вбудованими проблемами: SQL-ін'єкція, відсутня авторизація, N+1, секрет у коді, відсутня валідація, відсутні тести, блокуючий виклик в async, неточне обробляння помилок, плутана назва, змішані відповідальності | не читаючи списку, переглянути PR як ревʼюер і записати коментарі за категоріями: коректність, безпека, продуктивність, підтримуваність, тести | для кожного коментаря вказати серйозність (блокує злиття / бажано / дрібниця) і запропонувати виправлення | порівняти зі списком вбудованих проблем і записати, що пропущено і чому *Готово:* знайдено не менше 8 з 10 вбудованих проблем | для кожного коментаря є серйозність і конкретна пропозиція, а не лише «поганий код» | є хоча б 2 коментаря про те, що в PR зроблено добре | записано 2–3 пропущені проблеми та правило, яке допомогло б їх помітити (пункт власного чекліста ревʼю) *Перевірка:* чекліст.

## M. Патерни проєктування (Python-стиль)

Патерни тут не з підручника на класах, а так, як їх пишуть на Python: функції, декоратори, протоколи, `__init_subclass__`. Кожне завдання має автоперевірку (поведінка, а не структура коду). Ті самі патерни вже зустрічаються в інших розділах і позначені тегом *Патерн:* (Repository, Outbox, Circuit Breaker, Cache-Aside та інші).

147. 🟢 **Strategy:** правила знижок як функції з реєстром, нове правило без правок рушія. *Перевірка:* автотест. *Патерн:* Strategy, Registry
148. 🟡 **Unit of Work + Repository:** одна транзакція на бізнес-операцію, відкат за замовчуванням, атомарний переказ. *Перевірка:* автотест. *Патерн:* Unit of Work, Repository
149. 🟡 **Observer:** шина подій із підпискою на класи, знімком обробників та ізоляцією помилок (`ExceptionGroup`). *Перевірка:* автотест. *Патерн:* Observer
150. 🟡 **Декоратор, що не ламає функцію:** `functools.wraps`, підпис, `async`, методи, з дужками й без. *Перевірка:* автотест. *Патерн:* Decorator
151. 🟡 **State machine:** життєвий цикл замовлення як таблиця переходів із охоронцями та аналізом недосяжних станів. *Перевірка:* автотест. *CWE:* ~841 *Патерн:* State
152. 🟡 **Middleware chain:** ланцюжок обробників як у ASGI: порядок, переривання, повторне використання. *Перевірка:* автотест. *Патерн:* Chain of Responsibility
153. 🟡 **Adapter + Anti-corruption layer:** два платіжні провайдери в одну доменну модель, fail closed, переклад помилок. *Перевірка:* автотест. *CWE:* ~636, ~20 *Патерн:* Adapter, Anti-corruption layer
154. 🟡 **Specification:** правила з операторами `&`, `|`, `~`, ліниві обчислення й пояснення відмови. *Перевірка:* автотест. *Патерн:* Specification
155. 🟡 **Factory + автореєстрація плагінів** через `__init_subclass__`. *Перевірка:* автотест. *Патерн:* Factory, Registry
156. 🟡 **Parse, don't validate:** value objects, які неможливо створити невалідними, і `parse_order` з повним списком помилок. *Перевірка:* автотест. *CWE:* 20, ~915 *Патерн:* Value Object

## U. Архітектура ПЗ і проєктування

Коли код дедалі частіше пише AI, цінність розробника зміщується в рішення, які AI сам не ухвалить: де межі модулів, які інваріанти недоторканні, що станеться при відмові й як систему змінювати роками. Завдання тут перевіряють поведінку архітектурних механізмів, а документи вчать фіксувати й захищати рішення.

222. 🟡 **Fitness functions для модульного моноліту:** перевірка контрактів між модулями на AST: модулі імпортують одне одного лише через публічний `api`, заборонені напрямки (домен не знає про інфраструктуру), відсутність циклів, метрики Ca/Ce і нестабільності; звіт з ланцюжком імпорту для кожного порушення. *Перевірка:* автотести (дерево пакетів у `tmp_path`, без виконання коду). *Патерн:* Modular monolith, Fitness function
223. 🟡 **Aggregate з інваріантами:** агрегат «Замовлення» (рядки, ліміт суми, статуси), зміни лише через методи кореня, доменні події замість побічних ефектів, версія для optimistic locking, репозиторій зберігає агрегат цілком. *Перевірка:* автотести (інваріанти не обійти через вкладені обʼєкти, конфлікт версій). *CWE:* ~841 *Патерн:* Aggregate, Domain Event
224. 🟡 **Еволюція схем подій:** реєстр схем із режимами сумісності backward/forward/full (як у Schema Registry), заборона небезпечних змін (видалення обовʼязкового поля, зміна типу), upcasting старих версій подій під час читання. *Перевірка:* автотести. *Патерн:* Schema Registry, Upcaster
225. 🔴 **Event sourcing і CQRS:** стан агрегата з потоку подій, снапшоти, оптимістична перевірка версії при дописуванні, ідемпотентна проекція для читання з позицією (checkpoint), повна перебудова проекції без простою. *Перевірка:* автотести (повторна доставка подій, падіння посеред проекції). *Патерн:* Event Sourcing, CQRS
226. 🔴 **Мультитенантність fail closed:** доступ до даних лише через контекст tenant'а (запит без нього падає, а не повертає все), перевірка SQL-міграцій PostgreSQL: кожна таблиця з `tenant_id` має `ENABLE` і `FORCE ROW LEVEL SECURITY` та політику, кеш-ключі й імена обʼєктів у сховищі містять tenant. *Перевірка:* автотести (SQLite для репозиторію, аналізатор тексту міграцій). *CWE:* 639, 284, ~566 *Патерн:* Tenant isolation
227. 🟡 **Strangler fig з тіньовим трафіком:** маршрутизатор між legacy і новим сервісом: частка трафіку детермінована за ключем клієнта, режим shadow (відповідь з legacy, новий викликається паралельно й порівнюється з нормалізацією полів), автоматичний відкат маршруту при перевищенні частки розбіжностей. *Перевірка:* автотести (підроблені сервіси й годинник). *Патерн:* Strangler Fig, Dark launch
228. 🟡 **Hexagonal: ports & adapters:** переписати сервіс так, щоб домен не імпортував FastAPI, SQLAlchemy і SDK провайдерів. *Тип:* практика *Кроки:* обрати сервіс із власного проєкту (або capstone) з бізнес-логікою, змішаною з HTTP і SQL | описати порти як `typing.Protocol`: сховище, годинник, відправка повідомлень, LLM | перенести бізнес-правила в доменний модуль без імпортів фреймворків | написати два адаптери сховища: in-memory і SQLAlchemy | написати один набір контрактних тестів порту й прогнати його на обох адаптерах | додати fitness function (№222 або import-linter), що забороняє імпорт фреймворків у домені *Готово:* доменний модуль не імпортує FastAPI, SQLAlchemy чи SDK (перевіряє тест у CI) | контрактні тести однакові для обох адаптерів і обидва зелені | юніт-тести домену працюють без БД і мережі й займають менше секунди | є короткий ADR, чому межа портів проведена саме тут *Перевірка:* тести й fitness function у CI. *Патерн:* Hexagonal architecture, Ports and Adapters
229. 🟡 **ADR, C4 і design doc для capstone:** зафіксувати архітектуру Knowledge Assistant так, щоб нова людина (або агент) зрозуміла рішення без автора. *Тип:* документ *Кроки:* виписати 5–7 quality attributes з вимірюваними сценаріями (наприклад, «p95 /ask < 3 с при 20 RPS», «витік чужого документа неможливий навіть при помилці в сервісі») | намалювати C4 рівнів Context і Container (Structurizr DSL або Mermaid у репозиторії) | для 5 ключових рішень написати ADR (контекст, варіанти, рішення, наслідки): pgvector чи окрема векторна БД, ARQ чи Celery, модульний моноліт чи сервіси, як ізолюються користувачі, як підключається LLM | позначити bounded contexts (документи, пошук, чат, облік витрат) і зв'язки між ними | додати розділ «Режими відмов» і «Що свідомо не робимо» *Готово:* кожен quality attribute має число й спосіб перевірки | діаграми лежать у репозиторії як код і відповідають реальній структурі пакетів | є 5 ADR, у кожному щонайменше 2 розглянуті альтернативи й чесні мінуси обраного | межі контекстів збігаються з межами модулів у коді (перевіряє fitness function) | документ використовується як контекст для coding-агента (посилання з AGENTS.md/CLAUDE.md) *Перевірка:* ревʼю за чеклістом, частина віхи M10.
230. 🔴 🤖 **Architecture review дизайну від AI:** попросити моделі спроєктувати фічу й знайти, що в дизайні не так. *Тип:* документ *Кроки:* сформулювати фічу capstone з неочевидними вимогами (наприклад, спільні папки документів для команди з різними ролями й аудитом) | отримати дизайн від двох різних моделей з однаковим промптом | оцінити кожен за quality attributes з №229, режимами відмов, безпекою (межі довіри, авторизація, мультитенантність), вартістю й складністю міграції | знайти щонайменше 8 проблем: пропущені вимоги, неявні припущення, зайва складність, небезпечні дефолти | написати власний дизайн із ADR, де видно, що взято з AI-варіантів, а що відкинуто й чому *Готово:* таблиця порівняння двох дизайнів за однаковими критеріями | знайдено не менше 8 проблем, щонайменше 3 з них безпекові | кожна проблема має наслідок у продакшні, а не лише «так не роблять» | фінальний дизайн має ADR і план перевірки (тести, fitness functions, evals) | записано 3 питання, які варто ставити AI перед прийняттям будь-якого його дизайну *Перевірка:* ревʼю за чеклістом.

# Трек AI Engineering 🤖

Окремий трек із 8 етапів: від того, як працює LLM, до агентів, безпеки й регулювання. Завдання з позначкою *Тип:* автотест ще не мають папки в `tasks/`: умова вже фінальна, автоперевірка готується (на сайті значок «⏳ автотест готується»). Усі автотести працюють на мок-LLM і без мережі.

## N. Як працюють LLM: основи й математика

169. 🟡 **BPE-токенізатор з нуля:** навчити merges на корпусі, `encode`/`decode` без втрат (включно з емодзі й кирилицею), порахувати, у скільки разів український текст «дорожчий» за англійський. *Тип:* автотест *Перевірка:* автотести (roundtrip, детерміновані merges, кількість токенів).
170. 🟢 **Sampling:** softmax із temperature, top-k, top-p (nucleus), seed і logprobs; temperature 0 як greedy, перевірка розподілу на 10 000 вибірках. *Тип:* автотест *Перевірка:* автотести (статистичні межі з фіксованим seed).
171. 🔴 **HNSW з нуля:** багатошаровий граф, `M`, `ef_construction`, `ef_search`, видалення через tombstone; recall@10 проти brute force і кількість обчислень відстані. *Тип:* автотест *Перевірка:* автотести (recall ≥ 0.95 при ef=64, монотонність recall від ef).

181. 🔴 🤖 **Agentic RAG:** декомпозиція multi-hop питання, ітеративний пошук із переписуванням запиту, бюджет кроків, зупинка, коли контексту достатньо, і дедуплікація знайденого. *Тип:* автотест *Перевірка:* автотести (на мок-LLM: кількість кроків, recall на multi-hop наборі).
182. 🟡 **Інкрементальна індексація:** content hash, оновлення лише змінених чанків, видалення застарілих, переіндексація при зміні embedding-моделі, фільтр прав доступу в самому запиті пошуку. *Тип:* автотест *Перевірка:* автотести. *CWE:* 863, ~639

200. 🔴 🤖 **Red-team харнес:** корпус атак із мутаторами (base64, переклад, roleplay, розбиття на частини), прогін проти системи, attack success rate за категоріями OWASP LLM/Agentic, регресійний гейт. *Тип:* автотест *Перевірка:* автотести (на мок-системі).
201. 🟡 **Безпечне завантаження моделей:** сканер pickle-опкодів через `pickletools` (GLOBAL/REDUCE з небезпечними модулями), перевірка хешів, перевага safetensors. *Тип:* автотест *Перевірка:* автотести (без виконання pickle). *CWE:* 502, ~494
202. 🔴 🤖 **Red teaming власного capstone:** promptfoo, garak або PyRIT проти Knowledge Assistant. *Тип:* практика *Кроки:* описати модель загроз для AI-частини: недовірені джерела, інструменти, дані інших користувачів | налаштувати promptfoo (або garak чи PyRIT) з плагінами prompt injection, jailbreak, PII-витоку й excessive agency | додати власні атаки: документ з інструкцією, що отруює індекс; запит до чужих документів; ексфільтрація через посилання | прогнати, виправити знайдене і прогнати повторно *Готово:* є звіт із ASR до і після виправлень за категоріями OWASP | кожна знахідка має мітигацію або обґрунтоване прийняття ризику | набір атак запускається в CI проти мок-моделі *Перевірка:* чекліст.

212. 🟡 **Slopsquatting:** перевірка залежностей у коді, згенерованому AI: пакети, яких немає в знімку реєстру, схожі імена (відстань Левенштейна, підміна `-`/`_`), надто нові пакети без історії; рішення для pre-commit. *Тип:* автотест *Перевірка:* автотести (знімок реєстру як фікстура, без мережі). *CWE:* ~1357, ~829
213. 🔴 **Делеговані права агента:** агент діє від імені користувача через token exchange (RFC 8693): права звужуються до перетину прав користувача й задачі, токен короткоживучий і прив'язаний до ресурсу, ланцюжок `act` для аудиту, заборона ескалації між агентами. *Тип:* автотест *Перевірка:* автотести. *CWE:* 269, 863, ~441

## S. LLMOps, inference і моделі

141. 🟡 **Робота з AI-асистентами для коду:** `AGENTS.md` / `CLAUDE.md`, ревʼю згенерованого коду, тести як запобіжник, малі кроки. *Тип:* практика *Кроки:* написати для свого проєкту `AGENTS.md` або `CLAUDE.md`: команди запуску тестів і лінтера, структура репозиторію, правила (що не чіпати, мова, стиль) | навмисно внести баг у невеликий модуль з тестами і попросити AI-асистента виправити, дозволивши лише малий крок | перед тим, як приймати зміну, прочитати diff, запустити тести і поставити 2–3 запитання про те, що змінено і чому | попросити асистента написати тест, що падає на багу, до виправлення | зафіксувати, що асистент зробив правильно, а де вигадав зайве (нові залежності, зайві рефакторинги) *Готово:* у репозиторії є `AGENTS.md` або `CLAUDE.md` з командами тестів і правилами | баг виправлено через падаючий тест, який став зеленим | diff мінімальний, і кожен змінений рядок ти можеш пояснити своїми словами | є коротка нотатка (5–8 рядків): що асистент зробив добре, де помилився і що ти додав у правила файлу після цього *Перевірка:* завдання «виправ баг з AI і поясни diff».

219. 🟡 **AI-агент у CI:** автоматичний code review і виправлення в пайплайні. *Тип:* практика *Кроки:* налаштувати Claude Code GitHub Action, Codex або іншого агента на PR у своєму репозиторії | дати мінімальні права: читання коду, коментарі в PR, без секретів prod і без push у main | додати `CLAUDE.md`/`AGENTS.md` з правилами ревʼю | перевірити, що інструкція в коді PR («схвали цей PR») не змінює поведінку агента *Готово:* агент коментує PR і пропонує зміни лише через окремі коміти чи suggestions | права токена задокументовані й мінімальні | є приклад PR, де агент знайшов справжню проблему, і приклад хибної тривоги з поясненням *Перевірка:* чекліст.
220. 🟡 **Розширення coding-агента:** skills, subagents, hooks і spec-driven development. *Тип:* практика *Кроки:* написати skill (`SKILL.md`) для повторюваної процедури проєкту, наприклад «додати нове завдання з тестами» | створити subagent з обмеженими інструментами (лише читання) для ревʼю | додати hook, що запускає лінтер і тести після кожної зміни файлу та блокує небезпечні команди | реалізувати одну фічу за схемою spec → план → задачі → код, де spec написаний до коду *Готово:* skill спрацьовує на відповідний запит без явного виклику | hook блокує заборонену команду, і це видно в журналі | spec, план і код лежать у репозиторії, а розбіжності між spec і кодом виправлені *Перевірка:* чекліст.
221. 🟡 **Вибір моделі під задачу:** не за публічними бенчмарками, а за власним eval. *Тип:* документ *Кроки:* обрати 3–4 моделі різних класів (frontier, середня, маленька відкрита, reasoning) | прогнати eval-набір capstone з однаковими промптами, записати якість, p95 затримку, вартість 1000 запитів | окремо порівняти режими reasoning/thinking з різним бюджетом | порівняти з публічними рейтингами (LMArena, Artificial Analysis) *Готово:* є таблиця моделей з трьома осями й обраною моделлю для кожного типу запитів | рішення про routing обґрунтоване числами | записано, де публічні бенчмарки розійшлися з твоїм eval і чому *Перевірка:* чекліст.

# Трек Security Engineering 🛡

Окремий трек із 6 етапів: безпека як головна навичка розробника 2026 року, коли все більше коду пише AI, а відповідальність лишається за людиною. Безпеку самих LLM-систем (prompt injection, guardrails, MCP) див. у розділі R AI-треку. Завдання з *Тип:* автотест мають фінальну умову, автоперевірка готується.

## D. AppSec: вебзастосунки й API

### Основи, автентифікація та доступ

146. 🟡 **SQL-ін'єкція: виправ вразливий код:** параметри замість склеювання, екранування `LIKE`, allowlist для `ORDER BY`, обмеження `limit`. *Перевірка:* payload'и ін'єкцій на SQLite, чужі дані не витікають. *CWE:* 89, ~20

158. 🟡 **Open redirect:** безпечний `?next=` (`//evil.com`, `\`, таби, userinfo, схеми). *Перевірка:* автотест. *CWE:* 601
159. 🟡 **Log injection:** екранування керуючих символів і лапок, перевірка ключів, обрізання, один запис = один рядок. *Перевірка:* автотест із власним читачем логу. *CWE:* 117
161. 🟡 **Безпечний XML (XXE):** відмова від DOCTYPE, ліміти розміру, глибини й кількості елементів, UTF-16-обхід. *Перевірка:* автотест. *CWE:* 611, 776

57. 🟡 **CORS/CSP/заголовки:** налаштувати правильно, а не `*`. *Перевірка:* сканер заголовків. *CWE:* 942, 1021, ~319, ~200

## Y. Безпечна розробка з AI-агентами

Coding-агент (Claude Code, Codex, Cursor, Copilot) читає недовірений контент (репозиторій, issues, веб, MCP) і має доступ до shell, git і секретів: це та сама lethal trifecta, що й в AI-треку, але на твоїй машині й у CI. Тут вчимося, як зробити так, щоб агент писав код швидко і не відкрив двері зловмиснику. Пов'язане: етап «AI Security» (№197–199, №212) в AI-треку.

252. 🟡 **Детектор прихованих інструкцій у репозиторії:** сканер файлів, які читає агент (README, AGENTS.md, CLAUDE.md, `.cursor/rules`, коментарі, описи issue): невидимі символи Unicode (tag-символи U+E0000–E007F, zero-width, bidi-перемикачі як у Trojan Source), HTML-коментарі з імперативами до агента, base64-блоби, гомогліфи в іменах; позиція й декодований вміст кожної знахідки. *Перевірка:* автотести. *CWE:* ~1427, ~1007, ~451
253. 🟡 **Політика shell-команд для coding-агента:** рішення allow/ask/deny для команди: розбір `shlex`, пайпи, `;`, `&&`, `$(...)`, `bash -c`, `curl ... | sh`, `rm -rf` поза робочою текою, `git push --force`, читання `.env` і `~/.ssh`, мережа поза allowlist; deny має пріоритет, невідоме означає ask, пояснення рішення (як у hooks Claude Code). *Перевірка:* автотести (корпус обходів). *CWE:* 78, 22, ~250 *Патерн:* Policy Enforcement Point
254. 🔴 🤖 **CI-бот для issue triage без ін'єкцій:** агент на мок-LLM читає issue (недовірене) і має лише інструменти `add_label` і `comment`; текст issue ніколи не потрапляє в shell чи аргументи інших інструментів, лейбли з allowlist, коментар проходить output-фільтр (секрети, посилання поза allowlist, згадки людей), токен лише з `issues: write`, будь-яка зміна коду потребує людини. *Перевірка:* автотести (корпус шкідливих issues, у тому числі з прихованими інструкціями з №252). *CWE:* 1427, 77, ~269

## AI-проксі (як це працюватиме)

Більшість дешевих проксі й агрегаторів сумісні з форматом OpenAI. Тому в усіх завданнях з позначкою 🤖 провайдер налаштовується трьома змінними:

```
LLM_BASE_URL=https://твій-проксі/v1
LLM_API_KEY=...
LLM_MODEL=назва-моделі
```

- **Ключ нікуди не потрапляє в код і репозиторій:** лише `.env` локально та GitHub Secrets.
- **Автоперевірка в CI не залежить від ключа:** для тестів ми додаємо мок-LLM (детермінований сервер), тож завдання перевіряються безкоштовно й стабільно.
- **Реальний виклик за бажанням:** окремий режим `make live`, де той самий код працює проти твого проксі.
- **Безпека:** тримай проксі-ключ окремим з лімітом витрат; не вставляй його в публічні репозиторії та чати.
- Якщо проксі не повністю сумісний (наприклад, немає tool calling або streaming), завдання коректно позначаються як «недоступні на цій моделі».

## Jenkins

**Так, додаємо, але як окремий необов'язковий модуль**, а не основу.
- **Чому не основа:** у нових проєктах переважають GitHub Actions та GitLab CI. Jenkins лишається у великих компаніях і legacy-проєктах, де його підтримка часто потрапляє до джуніора. Тож знати його вигідно.
- **Що вчимо:** Jenkinsfile (declarative pipeline), агенти, Shared Libraries, credentials, запуск у Docker, інтеграція з Git-webhook.
- **Практика:** підняти Jenkins у `docker compose` локально, перенести пайплайн із завдань 73–75 на Jenkinsfile і порівняти з Actions.
- **Рівень:** 🟡, ставимо після основного блоку CI/CD.
