# №3 · Блокуючий код в async 🟡

**Ситуація.** Сервіс звітів на FastAPI раптом «зависає» під навантаженням, хоча CPU майже вільний. У `async def` ендпоінті викликається синхронна функція `render_pdf` (CPU або блокуючий I/O). Поки вона працює, event loop не може обслуговувати жоден інший запит: затримка росте в усіх, а не лише в того, хто просив звіт.

**Що зробити** у `solution.py` (`build_reports`):
- винеси синхронний рендер з потоку event loop;
- одночасно рендерити не більше `max_parallel` PDF;
- порядок результатів = порядок `user_ids`;
- збій рендеру одного користувача не ламає решту (`{"user_id": id, "error": "<текст>"}`).

**Підказки (без розв'язку):**
- `asyncio.to_thread(func, *args)` (Python 3.9+) або `loop.run_in_executor`;
- обмеження паралелізму робиться так само, як у №2;
- `await load_user(...)` вже неблокуючий, чіпати його не треба: знайти треба саме синхронний виклик у `async def`.

**Подумай (тести цього не покривають):**
- потоки допомагають із блокуючим I/O і з C-розширеннями, що відпускають GIL. Чисто Python-CPU-важке (наприклад, парсинг на чистому Python) у потоці все одно ділить GIL: там потрібен `ProcessPoolExecutor` або окремий воркер;
- у FastAPI звичайна `def`-функція ендпоінта вже виконується в пулі потоків. `async def` + блокуючий виклик гірше за просто `def`;
- як помітити проблему в production: метрика лагу event loop, `asyncio` debug mode (`PYTHONASYNCIODEBUG=1` показує «slow callback»).

**Перевірка:** `python check.py t03`. Спершу тести червоні. Тест не залежить від таймінгів: рендер чекає сигналу від іншої корутини, і лише вільний event loop дає її запустити.
