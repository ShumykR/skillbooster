# №130 · Покращення RAG: hybrid search, RRF, reranking, query rewriting 🔴 🤖

**Ситуація.** Базовий векторний RAG ловить зміст, але промахується на точних термінах: користувач вставляє код помилки `ERR-4012`, а embedding-модель про цей рядок нічого не знає. Класичний BM25 навпаки: знаходить `ERR-4012`, але для запиту «автомобіль» не помітить документ про «машину». Гібрид зливає обидва списки, reranker уточнює порядок, а переписування запиту виправляє питання, що залежать від контексту («а скільки це коштує?»).

**Що зробити** у `solution.py` (формули й формати в докстрингу):
- `tokenize` та `BM25` (idf, насичення частоти, нормалізація довжини);
- `rrf`: reciprocal rank fusion двох (чи більше) списків без потреби порівнювати їхні шкали score;
- `HybridIndex.search` з режимами `bm25`, `vector`, `hybrid`;
- `rewrite_query`: самостійний пошуковий запит із діалогу, з безпечним запасним варіантом;
- `rerank`: стабільне пересортування кандидатів зовнішнім scorer (імітація cross-encoder);
- `evaluate_ranking`: recall і MRR, щоб побачити «до/після».

**Підказки (без розв'язку):**
- BM25 рахує унікальні токени запиту, а рідкісні терміни отримують більшу вагу через idf;
- RRF використовує лише *позиції*, а не значення score: тому його можна застосовувати до списків із різних систем;
- результат `rewrite_query` це недовірений текст від моделі: порожню, надто довгу відповідь чи виняток слід замінити початковим питанням;
- порівнюй методи на одному еталонному наборі: у тесті BM25 дає recall 0.5, вектор 0.75, гібрид 1.0.

**Подумай:**
- чому reranker застосовують лише до top-N кандидатів (вартість cross-encoder пропорційна кількості пар «запит, документ»);
- як у PostgreSQL це робиться без окремої системи: `tsvector` + `pgvector` + RRF одним запитом;
- коли переписування запиту шкодить (втрата точних термінів, додавання вигаданих деталей) і як це ловити в eval (№131);
- як вибирати `k` у RRF та розмір `pool`.
