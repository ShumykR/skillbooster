# №32 · Партиціонування: планувальник партицій 🔴

**Ситуація.** Таблиця подій росте на десятки мільйонів рядків на місяць. Запит за один день сканує всю таблицю, а видалення старих даних (`DELETE ... WHERE created_at < ...`) годинами тримає блокування й роздуває таблицю. Помісячні партиції (`events_2026_03`) вирішують обидві проблеми: запит читає лише потрібну партицію (*partition pruning*), а видалення це миттєвий `DROP TABLE`. Але партиції треба *створювати наперед* (інакше вставка за 1-ше число падає) і прибирати за політикою зберігання.

**Що зробити** у `solution.py` (докстринг): генерація імен та DDL, `plan_partitions` (які партиції створити, а які видалити) і `partitions_for_range` (які партиції потрібно сканувати для діапазону дат). Це логіка, яку зазвичай запускає cron або `pg_partman`; SQL виконує окрема утиліта.

**Підказки (без розв'язку):**
- арифметику місяців роби через `рік * 12 + місяць - 1`, тоді перехід через грудень не потребує окремої гілки;
- діапазон партиції піввідкритий `[початок, кінець)`, як у `FOR VALUES FROM ... TO ...`: кінець не належить партиції;
- партицією *цієї таблиці* вважай лише імена строго вигляду `<таблиця>_YYYY_MM` (`fullmatch`): `events_default` або `events_archive` ніколи не видаляються, а `events_v2_2020_01` належить іншій таблиці;
- ім'я таблиці потрапляє в SQL, тож перевіряй його за allowlist-шаблоном (це CWE-89 для DDL, параметри тут не допоможуть).

**Подумай:**
- первинний ключ і унікальні індекси партиціонованої таблиці мають включати колонку ключа партиціонування;
- для запиту без умови за часом pruning не спрацює: перевір `EXPLAIN` (рядок `Subplans Removed`, у плані лише потрібна партиція);
- `DEFAULT`-партиція ловить рядки без партиції, але її розростання зазвичай сигналізує, що створення партицій наперед зламалось: став алерт;
- видалення партиції краще робити через `DETACH PARTITION CONCURRENTLY`, а потім архівувати чи видаляти.

**Перевірка:** `python check.py t32`. Лише стандартна бібліотека.
