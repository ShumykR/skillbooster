# №4 · Dependency injection та тестування 🟡

**Ситуація.** Конвертер валют бере курс прямим `httpx.get(...)` всередині ендпоінта, а історію веде в глобальному списку. Тести або б'ють у реальну мережу (повільно, нестабільно, ламаються вночі), або впливають один на одного через спільний стан.

**Що зробити** у `solution.py`:
- зробити залежності `get_rates()` (клієнт курсів) і `get_history()` (сховище історії) і підключити їх до обох ендпоінтів через `Depends`;
- перенести HTTP-виклик у `HttpRates.get_rate` (він кидає `RateUnavailable`, якщо курсу немає);
- прибрати глобальний `_HISTORY`;
- поведінка API не змінюється (докстринг у файлі).

Тести підміняють залежності через `app.dependency_overrides[get_rates] = ...` і **забороняють будь-яку мережу**: якщо хоч один виклик піде за межі процесу, тест падає.

**Підказки (без розв'язку):**
- залежність це звичайна функція, яку FastAPI викликає на кожен запит. Хочеш один спільний об'єкт на застосунок: створи його на рівні модуля або через `functools.lru_cache`, а `get_*` лише віддає його;
- ключем підміни у `dependency_overrides` є сама функція `get_rates`, тому ендпоінт має залежати саме від неї, а не від її результату чи класу;
- `Depends(get_rates)` у сигнатурі ендпоінта замінює глобальний імпорт/виклик.

**Подумай (тести цього не покривають):**
- фейк у тесті це не мок на бібліотеку (`patch("httpx.get")`): ти підміняєш *твій* інтерфейс, а не чужу реалізацію. Чому це стійкіше до рефакторингу?
- коли варто мати контрактний тест, який перевіряє справжній `HttpRates` проти sandbox-API, щоб фейк не розійшовся з реальністю?
- як підміна залежностей поєднується з авторизацією (підміна `get_current_user` у тестах) і з `lifespan` (пул з'єднань створюється раз)?

**Перевірка:** `python check.py t04`. Спершу тести червоні: на старому коді вони впираються в заборону мережі.
