# №162 · Mass assignment у FastAPI 🟡

**Ситуація.** Ендпоінт «оновити профіль» бере JSON з тіла й записує його в користувача: `user.update(body)`. Усе працює, поки клієнт шле `{"name": "Ann"}`. Але якщо він надішле `{"role": "admin"}` або `{"is_active": true}`, то стане адміном. Так зламали GitHub у 2012 році; у OWASP це CWE-915 (Mass Assignment), а в ширшому сенсі Broken Object Property Level Authorization (API3:2023).

**Що зробити:** у `solution.py` вже є вразливий застосунок. Перепиши його за вимогами докстрингу: окремі модельки *запиту* для звичайного користувача й для адміна, заборона зайвих полів, сувора типізація, модель *відповіді*, що не віддає `password_hash`, і порядок перевірок доступу. Тести ходять через `TestClient`.

**Підказки (без розв'язку):**
- pydantic v2: `model_config = ConfigDict(extra="forbid", strict=True)`: зайве поле це 422, а `"yes"` замість `true` не приводиться мовчки;
- `model_dump(exclude_unset=True)` відрізняє «поле не прислали» від «поле прислали як `null`»; `model_fields_set` теж;
- `response_model=...` у декораторі відфільтровує все, що не описано в моделі відповіді, навіть якщо функція віддала словник із зайвим;
- залежності (`Depends`) виконуються *до* валідації тіла: так перевірка доступу йде першою;
- перевірки ролі в обробнику теж недостатньо без заборони змінювати себе: інакше адмін випадково позбавить себе прав (або зловмисник, що перехопив сесію, закріпиться).

**Подумай (тести цього не покривають):**
- і для запиту, і для відповіді тримай *окремі* моделі: одна модель на все (`UserDB`) це і є джерело цієї вразливості;
- ORM-варіант того самого: `User(**request.dict())` або `setattr` у циклі; безпечний шлях це явний allowlist полів;
- ширше правило: автентифікація (хто ти), авторизація на рівні *ресурсу* (чи твій цей запис, завдання №52) і на рівні *властивості* (чи можна тобі змінювати саме це поле).

**Перевірка:** `python check.py t162`. Спершу частина тестів червона, і це нормально: вони ловлять вразливість. Потрібні `fastapi` та `httpx` (є в `requirements.txt`).
