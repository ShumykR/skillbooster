# №153 · Adapter і Anti-corruption layer 🟡

**Ситуація.** Інтеграція з двома платіжними провайдерами: один віддає `{"status": "succeeded", "amount": 1250}`, другий `{"state": "APPROVED", "total": "12.50"}`. Якщо їхні формати розтечуться по коду, то кожна зміна в API провайдера торкнеться десяти файлів, а нове значення статусу, якого ви не знали, зрештою «оплатить» замовлення. **Adapter** перекладає чужий формат у вашу модель на межі системи, а **anti-corruption layer** додає захист: усе недовірене перевіряється там, і далі мови провайдера ніхто не бачить.

**Що зробити** у `solution.py` (докстринг): `adapt` перекладає відповідь у `PaymentResult`, `Gateway.status` викликає мережу через `fetch` і перекладає ще й помилки.

**Підказки (без розв'язку):**
- гроші: рядок `"12.50"` розбирай у копійки цілочисельно (завдання №19), не через `float`;
- «fail closed»: що не розпізнано, те не «paid» і не мовчить, а дає помилку контракту;
- `re.fullmatch` + `[0-9]` замість `\d` (він приймає цифри будь-якого алфавіту) і замість `$` (він пропускає `\n` в кінці);
- `raise ... from exc` зберігає причину в `__cause__`;
- відповідь на запит про платіж `A` не має бути про платіж `B`: перевіряй ідентифікатор.

**Подумай:**
- адаптер можна описати через `Protocol`, а провайдерів реєструвати в реєстрі (завдання №155);
- зайві поля ми ігноруємо, бо провайдер може додавати нові, а відсутні поля вважаємо помилкою: чому така асиметрія;
- вебхуки від провайдера також треба перевіряти на справжність (завдання №41).
