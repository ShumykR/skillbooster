# №146 · SQL-ін'єкція: виправ вразливий код 🟡

**Ситуація.** Пошук користувачів зібрано через f-рядок: `f"... LIKE '{name_prefix}%' ORDER BY {sort_by}"`. Рядок `' OR '1'='1` повертає всю таблицю, `' UNION SELECT ...` витягує хеші паролів, а `ORDER BY` з параметра дозволяє підставити підзапит. SQL Injection це CWE-89, **№2 у MITRE CWE Top 25** (десятиліттями в першій десятці). Атаку відпрацюй на лабах [PortSwigger (SQL injection)](https://portswigger.net/web-security/sql-injection).

**Що зробити:** у `solution.py` уже є вразлива реалізація. Перепиши її за вимогами докстрингу. Тести подають до неї payload'и ін'єкцій і перевіряють, що нічого зайвого не витікає, таблиця не зникає, а чесні запити (разом з апострофами в іменах, `%` та `_`) працюють як раніше.

**Підказки (без розв'язку):**
- значення передавай параметрами (`?` у sqlite3, `%s`/`:name` в інших драйверах), драйвер сам їх екранує;
- параметр не допомагає для **імен колонок і напрямку сортування**: їх підставляють лише з allowlist;
- `LIKE` має власні спецсимволи (`%`, `_`): параметризація їх не нейтралізує, тож їх треба екранувати окремо (`ESCAPE`), інакше користувач керує шаблоном;
- «екранування лапок вручну» ненадійне (інші кодування, інший діалект БД): так не роби.

**Чого тести не покривають (подумай):**
- принцип найменших привілеїв: користувач БД застосунку без `DROP`/DDL і без зайвих таблиць;
- вторинна ін'єкція (безпечно збережене значення пізніше потрапляє в небезпечний запит) і NoSQL-ін'єкції (`{"$ne": null}`); ін'єкції в команди ОС шукає сканер із №56.
