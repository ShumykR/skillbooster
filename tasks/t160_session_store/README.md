# №160 · Керування сесіями 🟡

**Ситуація.** Сесія без кінця живе вічно: вкрадений cookie працює через рік. А якщо ідентифікатор сесії лишається тим самим до входу й після, то зловмисник, що підсунув жертві *свій* id (посилання, cookie з піддомену), після її входу сам стає залогіненим. Це CWE-384 (session fixation) і CWE-613 (недостатнє завершення сесії).

**Що зробити** у `SessionStore` (контракт у докстрингу): створення, читання, ротація id, відкликання, «вийти скрізь», обмеження кількості сесій і два види терміну дії: за неактивністю та абсолютний. Годинник і генератор id передаються ззовні, тому тести детерміновані.

**Підказки (без розв'язку):**
- ротація змінює *тільки* ідентифікатор: час створення лишається, інакше активна сесія ніколи не мала б абсолютного ліміту;
- «прострочена» перевіряється при кожному доступі, а не лише раз у хвилину: сесія, якої «ще не прибрав таймер», не повинна працювати;
- межа виключна: рівно `idle_ttl` секунд неактивності це вже кінець;
- `active_count` — спостереження, воно не має «подовжувати життя» сесії;
- колізія згенерованого id не повинна перезаписати чужу сесію.

**Подумай:**
- ротація id обов'язкова при вході, виході, зміні пароля та підвищенні привілеїв; зміна пароля має скидати *інші* сесії (`revoke_user`);
- у production сесії живуть у Redis із TTL (завдання №35), а в cookie лежить випадковий id з прапорцями `Secure`, `HttpOnly`, `SameSite` (завдання №143); у сховищі краще тримати *хеш* id, щоб витік Redis не давав готових сесій;
- stateless-токени (JWT, завдання №51) відкликати складно: тому в них короткий термін і refresh-токени, які вже зберігають на сервері.

**Перевірка:** `python check.py t160`. Лише стандартна бібліотека.
