# №156 · Parse, don't validate: типи, які не можна створити невалідними 🟡

**Ситуація.** Дані з запиту йдуть далі як `dict` та рядки, а перевірки розкидані по коду: десь `if "@" in email`, десь нічого. Один пропущений `if`, і в листі з'являється `\r\nBcc: evil@...` (ін'єкція в заголовки), у замовленні кількість `-5`, а клієнт сам виставляє собі `is_admin`. **Value object** з перевіркою в конструкторі перетворює «перевірили колись десь» на «якщо це `Email`, воно вже коректне». Це один зі способів закрити клас Insecure Design: невалідний стан неможливо виразити.

**Що зробити** у `solution.py` (докстринг): незмінні `Email`, `Quantity`, `Sku`, `Line`, `Order` та `parse_order`, яка перетворює «брудний» JSON на `Order` або повертає **усі** помилки разом із шляхами до полів.

**Підказки (без розв'язку):**
- `@dataclass(frozen=True)` + `__post_init__`: для нормалізації значення використай `object.__setattr__`;
- `bool` це підклас `int`: `isinstance(True, int)` істинне;
- `re.fullmatch` замість `re.match(...$)`: `$` дозволяє завершальний `\n`;
- збирай помилки в словник і піднімай один раз у кінці; не падай на першій;
- «зайве поле = помилка»: так працює allowlist полів проти mass assignment (CWE-915).

**Подумай:**
- у FastAPI це ідея pydantic-моделей (`extra="forbid"`, `StrictInt`, `conint`); спробуй переписати тут `parse_order` на pydantic і порівняти повідомлення про помилки;
- валідація формату `Email` не доводить, що скринька існує: це робить лист із підтвердженням;
- межі (`1..50` рядків, `10**12`) це також захист від DoS та переповнення в інших системах.

**Перевірка:** `python check.py t156`. Лише стандартна бібліотека.
