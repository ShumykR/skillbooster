# №75 · Збірка та публікація образу: теги за версією й sha 🟡

**Ситуація.** CI збирає Docker-образ і пушить його в GHCR/ECR. Дрібні рішення про теги потім болять на production: образ із чужого PR опинився в реєстрі; тег `1.2.3` перезаписали іншим вмістом, і «та сама» версія поводиться по-різному; випустили hotfix `1.2.5` для старої гілки, і `latest` відкотив усіх на стару лінію; ніхто не знає, з якого коміту зібрано образ `latest`.

**Що зробити** у `solution.py`: функція `image_tags(event, ref, sha, ...)` вирішує, чи публікувати образ і з якими тегами (це те, що робить `docker/metadata-action`, тільки тут ти бачиш усі правила). Точні правила для PR, гілок, релізних тегів і pre-release у докстрингу файлу.

**Підказки (без розв'язку):**
- версії порівнюй кортежами чисел `(1, 10, 0)`, а не рядками (`"1.10.0" < "1.9.0"` за алфавітом);
- плаваючий тег (`1.2`, `1`, `latest`) ставиться, лише якщо нова версія найбільша у своїй лінії, у своєму мажорі й в усьому реєстрі відповідно;
- теги з sha (`sha-0123456`) дають однозначний звʼязок «образ ↔ коміт» і не змінюються;
- повний тег `X.Y.Z` має бути *незмінним*: якщо він уже є, нічого не публікуй.

**Подумай (тести цього не покривають):**
- у production деплой краще прив'язувати до **digest** (`image@sha256:...`), а не до тегу: тег можна пересунути, digest ні (див. також завдання №69 про `:latest` у Dockerfile);
- ECR має налаштування immutable tags: реєстр сам забороняє перезапис; увімкни його;
- мульти-архітектурні образи (`linux/amd64`, `linux/arm64`) через `docker buildx` і `manifest list`: один тег, кілька образів;
- підпис образу (cosign) і SBOM, прив'язані до digest, а не до тегу;
- прибирання: політики життєвого циклу (lifecycle) для старих `pr-*` і `sha-*` тегів, інакше реєстр росте без меж.

**Перевірка:** `python check.py t75`. Спершу тести червоні. Лише стандартна бібліотека.
