# №97 · Налагодження pod'ів: що саме зламалось 🟡

**Ситуація.** `kubectl get pods` показує `CrashLoopBackOff`, `ImagePullBackOff`, `Pending`, `CreateContainerConfigError`. Заголовок статусу це лише симптом: за одним `CrashLoopBackOff` ховаються OOM, падіння на старті, невдала liveness-проба, відсутній `command`. Досвідчений інженер за 30 секунд перебирає `describe`, `events`, `lastState`, `exitCode`. Зафіксуй цей порядок міркувань кодом.

**Що зробити** у `solution.py` (формат вхідного JSON і таблиця правил у докстрингу):
- `diagnose(pod, events)` повертає заголовок проблеми, корінну причину, контейнер і деталь;
- `triage(pods)` групує набір pod'ів за проблемою, як робив би черговий вранці після невдалого релізу.

**Підказки (без розв'язку):**
- порядок правил важливий: `Evicted` і `Pending` дивляться на pod загалом, контейнери лише після них, а init-контейнери раніше за основні;
- `OOMKilled` майже завжди ховається в `lastState.terminated`, бо поточний стан вже `CrashLoopBackOff`;
- exit code `128 + N` означає сигнал `N`: 137 це SIGKILL (9), 139 SIGSEGV (11), 143 SIGTERM (15); 126 і 127 дає shell, коли команда не виконується чи не знайдена;
- повідомлення Kubernetes порівнюй без урахування регістру, а з тексту `secret "x" not found` ім'я дістає регулярний вираз.

**Подумай:**
- чому liveness-проба, що перевіряє базу, перетворює короткий збій БД на хвилю перезапусків усіх pod'ів;
- чим `requests` відрізняється від `limits` для `Pending` і для `OOMKilled` (планувальник дивиться на перше, kubelet на друге);
- як відрізнити «застосунок завершується з кодом 0» від «Deployment з командою, що не лишається в foreground»;
- коли `kubectl logs --previous` єдиний спосіб побачити причину.

**Перевірка:** `python check.py t97`. Лише стандартна бібліотека. Далі: на kind/Killercoda зламай навмисно чотири Deployment'и (неіснуючий тег, відсутній Secret, `memory: 10Mi`, `command: ["false"]`) і розберися лише за `kubectl describe pod` та `kubectl get events`.
