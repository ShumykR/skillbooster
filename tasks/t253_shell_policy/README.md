# №253 · Політика shell-команд для coding-агента 🟡

**Ситуація.** Coding-агент пропонує shell-команди, і кожна «Allow» від людини це довіра наосліп: `rm -rf` із зайвим `..`, `curl ... | sh`, `git push --force`, `cat .env` усередині `$(...)` чи `bash -c`. Модель не є межею безпеки, тому рішення «виконати, спитати чи заборонити» ухвалює код ДО запуску, як у hooks Claude Code (`PreToolUse`). Це Policy Enforcement Point: простий, детермінований і перевірюваний корпусом обходів.

**Що зробити** у `solution.py` (повні правила, імена правил і пріоритети в докстрингу): `decide(command, *, cwd, workspace, allowed_hosts=(), home="/home/dev")` повертає `{"decision", "rule", "reason"}`. Команду ніколи не виконуй, лише розбирай текст. Тести це корпус із близько 280 команд: чесні (allow), небезпечні й обхідні (deny), сумнівні й невідомі (ask).

**Підказки (без розв'язку):**
- `shlex` добре ріже слова, але не знає про `;`, `&&`, `|` у «склеєному» вигляді (`a;b`), про `$(...)` і зворотні лапки; подумай, чи достатньо одного проходу, чи потрібен свій маленький розбір із підтримкою лапок;
- вкладені команди та `bash -c '...'` це нові команди: оцінюй їх так само й бери найсуворіше рішення; чому «слово зі вставкою» не можна вважати безпечним шляхом?
- «усередині workspace» перевіряй після нормалізації шляху (`..`, `~`, `$HOME`) і з урахуванням `cd` раніше в тому ж рядку; чому `startswith("/work/proj")` без роздільника хибний?
- `deny` має бути вищим за `ask` за будь-якого порядку команд у рядку; як це зробити, не плутаючи нескінченними `if`?
- таблиця «команда → правило» краще за ланцюжок умов: нову команду додаєш рядком, а не гілкою;
- allowlist мережі порівнюй з **хостом**, розібраним як URL, а не з підрядком: `https://pypi.org.evil.example` і `http://pypi.org@evil.example`.

**Подумай:**
- чому allowlist команд надійніший за denylist (`rm`, `curl`), і де межа, коли allowlist стає надто нудним для користувача (ask fatigue)?
- що політика принципово не бачить: символічні посилання, вміст скриптів (`make`, `npm test`), змінні середовища, `alias`. Яка друга лінія захисту (контейнер/devcontainer без секретів, мережевий egress-фільтр, мінімальні права токенів, №257)?
- як тримати таку політику в конфігу (YAML) і тестувати її корпусом обходів у CI при кожній зміні (regression на знайдені обходи)?
- чим відрізняється рішення `ask` у hooks від `deny` для агента, що працює без людини (CI): що має робити `ask` там?

**Перевірка:** `python check.py t253` (корпус обходів). Лише стандартна бібліотека. Далі: підключи `decide` як `PreToolUse`-hook для Bash у власному проєкті й подивись, скільки справжніх команд агента потрапляє в `ask`.
