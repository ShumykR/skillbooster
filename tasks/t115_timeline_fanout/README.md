# №115 · Тайм-лайн: fan-out on write проти fan-out on read 🔴

**Ситуація.** У соцмережі стрічка користувача це пости тих, на кого він підписаний. Якщо рахувати її при кожному відкритті застосунку (pull), читання повільне: треба злити списки сотень авторів. Якщо розсилати кожен пост у «скриньку» підписників (push), читання миттєве, але зірка з мільйоном підписників на кожен пост робить мільйон записів. Інженерне рішення гібридне: розсилати звичайних авторів, а зірок підтягувати при читанні.

**Що зробити** у `solution.py` (точні правила в докстрингу): клас `Timeline` з трьома стратегіями `push`, `pull`, `hybrid`:
- публікація, підписка (діє лише на пости *після* підписки) та відписка;
- стрічка з курсорною пагінацією (`cursor` = id останнього поста сторінки);
- `stats["fanout_writes"]`: скільки записів у скриньки зроблено, щоб побачити різницю у вартості;
- головна вимога: усі три стратегії повертають **однакові** стрічки.

**Підказки (без розв'язку):**
- у push-стратегії відписка не видаляє пости зі скриньки, тому фільтруй при читанні за поточними підписками й моментом підписки;
- гібрид читає і скриньку, і списки «зірок», тому обʼєднувати треба множиною id, щоб не було дублів;
- для сторінки візьми на один пост більше за `limit`: так без додаткового запиту ясно, чи існує наступна сторінка;
- статус «зірки» в завданні липкий: це спрощує узгодженість (пост, який не розіслали, повинен читатись через pull).

**Подумай:**
- чому cursor за id краще за `offset` (стрічка змінюється, поки користувач гортає);
- як у справжньому Redis це лежить: `ZADD feed:{user}` з score = id, `ZREVRANGEBYSCORE` для сторінки, обмеження довжини скриньки (`ZREMRANGEBYRANK`);
- що робити з неактивними користувачами (не розсилати їм, а збирати стрічку при першому вході);
- як видалення поста або блокування автора відображається в уже розісланих скриньках.
