# №177 · Constrained decoding 🔴

**Ситуація.** Просити модель «поверни валідний JSON» ненадійно: вона лише оцінює ймовірності наступного токена, і раз на тисячу відповідей зламає дужку чи додасть коментар, а парсер у production впаде. Constrained decoding (Outlines, xgrammar, llguidance) на кожному кроці маскує токени словника, що зробили б префікс невалідним. Тоді невалідний JSON фізично неможливий.

**Що зробити** у `solution.py` (точні правила та підмножина JSON Schema в докстрингу):
- `valid_prefix`, `is_complete`: скінченний автомат для канонічного компактного JSON;
- `token_mask`: маска допустимих токенів для префікса (токен може перетинати межі елементів);
- `constrained_generate`: цикл «маска → вибір моделі → дописати токен» з помилками для нечесної моделі й глухих кутів.

«Модель» це функція `choose(text, allowed)`, яку передає тест, тож мережі й LLM немає.

**Підказки (без розв'язку):**
- автомат зручно описати станом (позиція в схемі + що вже зібрано всередині поля), а не регулярним виразом: що тобі треба пам'ятати всередині рядка з екрануванням і лічильником `maxLength`?
- `valid_prefix(text + токен)` для кожного токена це простий, але повільний спосіб: коли його достатньо, а коли варто рахувати стан інкрементально?
- чим «префікс повного документа» відрізняється від «повного документа» і чому символ після кінця документа це помилка?
- цілі числа: які префікси допустимі (`-`, `0`, `-0`?) і коли число «можна завершити»?
- що має зробити генератор, коли словник не вміє продовжити неповний документ (наприклад, немає токена `"`)?

**Подумай:**
- чому маска, що блокує валідні продовження, гірша за відсутність маски (модель «ламається» на нетипових символах)?
- маскування змінює розподіл ймовірностей: що буде з якістю відповіді, якщо схема змушує модель до значення, якого вона «не хоче»?
- як цей підхід співвідноситься зі structured outputs у API провайдерів і з валідацією відповіді Pydantic після генерації (завдання №127)?
