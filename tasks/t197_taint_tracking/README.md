# №197 · Taint tracking у стилі CaMeL 🔴

**Ситуація.** Prompt injection неможливо надійно «відфільтрувати»: будь-який текст зі сторінки, листа чи відповіді інструмента може містити інструкції для моделі. Зате можна обмежити, **що** недовірені дані можуть робити. Ідея CaMeL (Google DeepMind, 2025): довірена модель бачить лише запит користувача й будує план; недовірені дані обробляє ізольована модель без інструментів; звичайний код стежить за походженням значень і не дає недовіреному керувати адресатом листа чи URL.

**Що зробити** у `solution.py` (точний API в докстрингу): тип `Tainted` із джерелами, операції, що поширюють походження (`derive`, `join`, `fmt`, `get`), `ToolRegistry` із чутливими аргументами й `run_agent`, що виконує план від довіреного планувальника. Порушення політики це `PolicyViolation` з іменем інструмента, аргументу й джерелами.

**Підказки (без розв'язку):**
- походження поширюється на все, що **обчислено** з недовіреного значення: яка операція над джерелами правильна при злитті двох значень?
- перевірка чутливого аргумента має бути в одному місці перед викликом, а не в кожному інструменті: чому «забути» перевірку тоді неможливо?
- чи може недовірене значення впливати на **вибір** інструмента або гілку виконання, а не лише на аргумент? Де це блокувати?
- результат довіреного інструмента (`trusted_result`) і результат інструмента, що читає зовнішній світ, мають різне походження: як це виразити?
- що саме не можна робити з `Tainted` у звичайному Python (наприклад, неявно перетворювати на `str`) і чому це частина захисту?

**Подумай:**
- чого цей підхід не вирішує (приховані канали, відповідь користувачу, текст листа з недовірених даних) і що потрібно додатково (human-in-the-loop, завдання №196)?
- ціна: недовірені дані стають «слабшими» у плані; для яких сценаріїв це неприйнятно?
- звʼязок з CWE-807 (рішення на недовіреному вході) і CWE-863, з capstone (M4/M6).
