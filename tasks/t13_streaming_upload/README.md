# №13 · Потокове завантаження файлів 🟡

**Ситуація.** Ендпоінт «завантажити відео» читає тіло запиту цілком (`await request.body()` або `UploadFile.read()`), і лише тоді перевіряє розмір. Двоє користувачів із файлами по 2 ГБ кладуть сервіс з нестачею пам'яті, а атакуючому для DoS достатньо надсилати великі тіла (CWE-770: ресурси без обмеження).

**Що зробити** у `solution.py` (`save_upload`): приймати потік шматків, писати на диск одразу, рахувати розмір на льоту й обривати завантаження після перевищення ліміту. Повні вимоги в докстрингу файлу.

**Підказки (без розв'язку):**
- `async for chunk in chunks:` читає по шматку; накопичуй лише лічильник байтів;
- пиши у тимчасовий файл у **тій самій теці** (`tempfile.NamedTemporaryFile(dir=..., delete=False)` або `dest.with_suffix(...)`), а в кінці `os.replace(tmp, dest)`: перейменування в межах однієї файлової системи атомарне;
- `try / except BaseException / finally`: тимчасовий файл видаляється при будь-якому виході, крім успіху (у т.ч. при `CancelledError`);
- ліміт перевіряй *до* запису шматка, що його перевищує.

**Подумай (тести цього не покривають):**
- заголовок `Content-Length` можна підробити або взагалі не надіслати (chunked), тому довіряти можна лише лічильнику, що веде сервер; заголовок корисний для швидкої відмови до читання;
- запис на диск у `async`-коді блокує event loop (завдання №3): для великих файлів використовуй `aiofiles` або `asyncio.to_thread` для запису;
- для файлів більше за сотні МБ краще, щоб файл взагалі не проходив через бекенд: presigned URL/POST до S3 з умовою `content-length-range`, бекенд лише видає дозвіл і приймає webhook про завершення;
- що перевіряти про *вміст* файлу, див. завдання №145; шлях збереження і ім'я файлу, див. №144. Тут лише розмір і ресурси.

**Перевірка:** `python check.py t13`. Пам'ять вимірює `tracemalloc` на потоці 40 МБ: пік понад 2 МБ означає, що файл утримується в пам'яті.
