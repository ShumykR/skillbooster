# №25 · Транзакції та аномалії ізоляції 🟡

**Ситуація.** Двоє користувачів одночасно поповнюють той самий баланс: обидва прочитали `100`, обидва записали `100 + внесок`, і одне поповнення тихо зникло. У тестах із послідовними запитами цього ніколи не видно. Така поведінка залежить від **рівня ізоляції** транзакцій, а аномалії мають назви: dirty read, non-repeatable read, lost update, write skew.

**Що зробити** у `solution.py` (докстринг): працюємо з *розкладом* (schedule), тобто списком операцій `("read", "T1", "x")`, `("commit", "T2")` у порядку виконання. `find_anomalies` знаходить у розкладі чотири аномалії, `anomalies_allowed` повертає, що дозволяє кожен рівень ізоляції PostgreSQL, а `violations` поєднує їх: що в розкладі не могло б статися на заданому рівні. Справжня БД не потрібна, тож тести детерміновані.

**Підказки (без розв'язку):**
- для кожної аномалії є невеликий *шаблон* у послідовності, який можна шукати перебором; записуй його одним реченням, перш ніж писати код (наприклад, lost update: «T1 прочитала x, потім T2 записала x, потім T1 записала x, обидві зафіксовані»);
- «раніше» означає індекс в розкладі; зручно спершу перетворити розклад на позиції commit/abort кожної транзакції;
- результат це відсортований набір *унікальних* кортежів, тому повторні читання не множать знахідки;
- перевіряй вхід: операція транзакції без `begin` чи після `commit` це помилка розкладу.

**Подумай (з реальною БД):**
- у PostgreSQL `REPEATABLE READ` це знімок: lost update там не буде, а закінчиться помилкою серіалізації, яку клієнт має обробити повтором транзакції; `SERIALIZABLE` ловить і write skew;
- альтернативи вищому рівню ізоляції: `SELECT ... FOR UPDATE` блокує рядок (pessimistic), версійне поле (завдання №27) робить це оптимістично, а `UPDATE ... SET balance = balance + 100` складає операцію в одному запиті;
- write skew (двоє лікарів знімають себе з чергування) ловить лише `SERIALIZABLE` або явне блокування, тому знати цю аномалію варто;
- відтвори lost update руками: дві сесії `psql` у `docker run postgres`, `BEGIN; SELECT ...` у порядку з розкладу.

**Перевірка:** `python check.py t25`. Лише стандартна бібліотека.
