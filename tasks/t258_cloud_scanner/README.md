# №258 · Сканер хибних налаштувань хмари 🟡

**Ситуація.** Більшість витоків у хмарі це не «злам», а хибне налаштування: бакет, відкритий усьому інтернету, база з `PubliclyAccessible`, порт 22 для `0.0.0.0/0`, вимкнений CloudTrail, інстанс, що віддає IAM-токени через IMDSv1 (так вкрали дані Capital One). Прапорців багато, а ефективна публічність бакета залежить від політики, ACL і Block Public Access разом, на рівні бакета й акаунта. Інструменти на кшталт Prowler, ScoutSuite і AWS Config роблять саме це, а ти напишеш ядро такого сканера.

**Що зробити** у `scan_account` (точні правила, формат знімка й порядок знахідок у докстрингу): прочитати JSON-знімок акаунта (як злитий вивід `describe`-викликів) і повернути знахідки з `severity` і порадою `fix`: публічні S3, відкриті security groups, IMDSv1, CloudTrail, KMS без ротації, публічні RDS.

**Підказки (без розв'язку):**
- «ефективний» прапорець Block Public Access це не прапорець бакета, а його поєднання з акаунтним; яке саме? Подумай, що для безпеки означає «хоч одне місце заборонило»;
- чотири прапорці роблять різні речі: який із них нейтралізує вже існуючий публічний ACL, який існуючу публічну політику, а які лише не дозволяють створити нову?
- `Principal: "*"` з умовою `aws:PrincipalOrgID` це не публічний доступ; а з умовою `aws:UserAgent`?
- діапазон портів це інтервал: перевір межі й правило «усі порти», яке не повинно давати ще й три окремі знахідки;
- як зробити так, щоб одне правило для одного ресурсу не повторювалось, навіть коли шляхів до проблеми кілька?

**Подумай:**
- чому сканер за знімком не бачить IAM-політик користувачів і SCP, і як це врахувати у висновках («немає знахідок» ≠ «безпечно»)?
- як перетворити такий сканер на preventive-контроль: Terraform-перевірка до `apply` (завдання №84) і SCP, що забороняє вимикати Block Public Access (№92)?
- що важливіше для triage: severity ресурсу чи те, чи він справді досяжний ззовні (мережевий шлях, WAF, чи містить бакет чутливі дані)?
