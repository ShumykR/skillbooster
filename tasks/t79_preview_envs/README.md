# №79 · Preview-середовище на кожен PR 🟡

**Ситуація.** Ревʼюер не хоче клонувати гілку й піднімати все локально, щоб подивитись на зміну: йому потрібен URL `pr-123-new-checkout.preview.example.com`. Такі середовища створюються автоматично на кожен PR і мають зникати, коли PR закрито. Інакше за тиждень у хмарі висить сорок «тимчасових» стендів, і рахунок це відчуває; або стенд застарів і показує вчорашній код.

**Що зробити** у `solution.py`:
1. `preview_name`: безпечне DNS-імʼя з номера PR і назви гілки (`feature/Login_Page` дає `pr-12-feature-login-page`, не довше за 40 символів);
2. `plan_previews`: планувальник, що за відкритими PR і наявними середовищами повертає дії `create`/`update`/`destroy`/`skip`: закриті й прострочені середовища знищуються, нові коміти оновлюють, мітки `no-preview` і `keep-preview` дають винятки, а квота `max_envs` обмежує витрати.

Точні правила (порядок рішень, квоти, порядок результату) у докстрингу файлу. Планувальник нічого не робить у хмарі: він лише повертає список, а виконує його окремий крок. Так його можна перевірити без хмари.

**Підказки (без розв'язку):**
- спочатку визнач, які середовища *лишаються*: лише потім відомо, скільки вільних слотів;
- порядок перевірки для наявного середовища має значення: закритий PR, потім `no-preview`, потім термін (`expired`, якщо немає `keep-preview`), і лише потім питання про `update`;
- у `slug` дозволяй тільки `[a-z0-9-]`: слеші, підкреслення, кирилиця й великі літери ламають DNS або URL;
- обрізання імені може лишити `-` на кінці: прибери його вдруге.

**Подумай (тести цього не покривають):**
- безпека: preview-середовище з чужого форка не повинно отримувати production-секрети (`pull_request_target`, див. №73); дані в preview мають бути синтетичними, а не копією production (GDPR, №62);
- вартість: у Kubernetes це namespace на PR (`kubectl delete ns` знищує все одразу), у Terraform окремий workspace; у ECS окремий сервіс; ефемерні БД через `neon branches`/`pg_dump`-шаблони;
- хто прибирає, якщо подія `closed` загубилась? Це причина планувальника, що звіряє стан, а не лише реагує на події: періодичний «reconcile»-цикл знищує сиріт;
- вебхук/GitHub Action `pull_request: [opened, synchronize, reopened, closed]` і коментар у PR із URL, щоб ревʼюер знайшов стенд;
- обмеження ресурсів і TTL важливіші за красу: краще передбачуваний `ttl` та ліміт у $, ніж «всі PR назавжди».

**Перевірка:** `python check.py t79`. Спершу тести червоні. Лише стандартна бібліотека.
