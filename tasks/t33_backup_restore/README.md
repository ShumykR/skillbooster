# №33 · Резервні копії та відновлення на момент часу (PITR) 🟡

**Ситуація.** Хтось о 14:07 виконав `DELETE FROM orders` без `WHERE`. Нічна копія була о 03:00, тож відновлення з неї втратить 11 годин даних. Потрібне **відновлення на момент часу** (PITR): базова копія плюс безперервний ланцюжок WAL-сегментів, які програються до 14:06. Вся схема тримається на двох речах: ланцюжок WAL без жодного пропуску і те, що відновлення *справді перевірено*, а не лише налаштовано.

**Що зробити** у `solution.py` (докстринг): `plan_restore` обирає найновішу придатну базову копію й діапазон WAL для заданого моменту, `prune_backups` реалізує політику зберігання «дід-батько-син» (щоденні, щотижневі, щомісячні), а `removable_wal` каже, які WAL-сегменти вже ніхто не потребує. Усе працює над метаданими, самих файлів та Postgres тут немає.

**Підказки (без розв'язку):**
- копія стає узгодженою лише після `end_seq`, тому відновлювати треба щонайменше до цього сегмента, навіть якщо `target` раніший;
- сегмент, що *містить* момент `target`, це перший із `ends_at >= target`;
- перевірка безперервності це «усі цілі числа від `start_seq` до `wal_to` присутні»; WAL з архіву може прийти невпорядкованим і з повторами;
- для політики зберігання зручно групувати копії за періодом (день, `(рік, ISO-тиждень)`, `(рік, місяць)`) і брати найновішу в кожному періоді вікна;
- ISO-тиждень не збігається з календарним роком: 29 грудня 2025 це вже тиждень 1 року 2026.

**Подумай:**
- копія, яку жодного разу не відновлювали, це припущення. Автоматизуй щотижневе відновлення в чистий інстанс і порівняння контрольних сум чи кількості рядків критичних таблиць;
- правило 3-2-1: три копії, на двох типах носіїв, одна поза основним регіоном/акаунтом (S3 з Object Lock захищає від видалення зловмисником);
- логічний `pg_dump` зручний для невеликих баз і міграцій між версіями, а фізична копія + WAL (pgBackRest, WAL-G, barman) для великих і для PITR;
- у RDS/Aurora це вмикається налаштуванням (automated backups + PITR), але «відновити» означає *новий* інстанс і перемикання застосунку, тож відпрацюй сценарій заздалегідь.
