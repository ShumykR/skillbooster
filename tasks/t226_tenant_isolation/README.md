# №226 · Мультитенантність fail closed 🔴

**Ситуація.** SaaS тримає дані сотень клієнтів в одній базі. Один забутий `WHERE tenant_id = ?` у новому ендпоінті, одна міграція без `FORCE ROW LEVEL SECURITY`, один кеш-ключ `user:42` без префікса, і клієнт A читає дані клієнта B. Це CWE-639 (обхід авторизації через ключ) і CWE-284, а в OWASP API Top 10 цей клас називають Broken Object Level Authorization. Головний принцип: коли контексту tenant'а немає, система падає, а не віддає «все».

**Що зробити** у `solution.py` (точні правила в докстрингу):
- `tenant_context` і `current_tenant`: контекст на `contextvars`, вкладення, ізоляція між asyncio-задачами, валідація id;
- `NoteRepository` над SQLite: усі операції беруть tenant лише з контексту, без нього падають ДО будь-якого SQL, чужі рядки не бачать, не змінюють і не видаляють;
- ключі кешу й сховища: однозначний формат, захист від виходу за префікс (`..`, префікс `ab` проти `abc`), `TenantCache` з очищенням лише свого простору;
- `audit_migration`: аналізатор тексту міграцій PostgreSQL: кожна таблиця з `tenant_id` має `ENABLE` і `FORCE ROW LEVEL SECURITY` та політику, що справді обмежує за `tenant_id`; `DISABLE`, `NO FORCE` і ролі `BYPASSRLS` це знахідки.

**Підказки (без розв'язку):**
- звичайна глобальна змінна «поточний tenant» ламається, щойно два запити виконуються конкурентно: яку примітивну структуру Python створено саме для цього?
- де правильно перевіряти наявність контексту: у кожному методі окремо чи в одному місці, і чому важливо, щоб це відбувалось до першого запиту до БД?
- «чужий рядок не знайдено» і «рядок заборонено» для клієнта різні відповіді: яка з них не розкриває, що чужий id існує?
- для шляху в сховищі перелік *дозволених* символів надійніший за перелік заборонених; а що робить префіксна перевірка `startswith("tenants/ab")` з tenant'ом `abc`?
- у SQL-тексті небезпечні не лише ключові слова, а й місця, де вони лише згадані: у коментарі, у рядку, у тілі функції. Як зробити аналіз стійким до цього, зберігши номери рядків?
- чому політика `USING (true)` гірша за відсутню політику (подумай про те, що бачить людина, яка переглядає лише `\d+ table`)?

**Подумай:**
- `FORCE ROW LEVEL SECURITY` потрібен, бо власник таблиці за замовчуванням обходить політики; а суперкористувач і роль із `BYPASSRLS` обходять їх завжди: хто в твоєму середовищі міграцій/застосунку під якою роллю працює?
- як передати tenant у PostgreSQL (`SET LOCAL app.tenant_id` у транзакції, `current_setting(..., true)`) і що станеться з пулом зʼєднань, якщо забути `LOCAL`?
- schema-per-tenant чи database-per-tenant проти спільних таблиць: ціна ізоляції проти ціни міграцій (capstone M2, M3);
- фонові задачі й воркери (ARQ у capstone) не мають HTTP-контексту: звідки вони беруть tenant і чому падіння краще за «system» tenant?

**Перевірка:** `python check.py t226`. Лише стандартна бібліотека (`sqlite3`, `contextvars`, `re`). Далі: прожени аналізатор на справжніх міграціях Alembic свого проєкту і додай правило для `CREATE VIEW` без `security_invoker`.
