# №139 · Асинхронні LLM-завдання: черга, прогрес через SSE, скасування 🟡 🤖

**Ситуація.** Генерація звіту моделлю займає 2–3 хвилини. HTTP-запит стільки не триматимуть ні проксі, ні браузер. Правильна схема: `POST /reports` повертає `202` і `job_id`, воркер працює в окремому процесі й публікує прогрес, а клієнт слухає `GET /jobs/{id}/events` (SSE). Якщо зʼєднання обірвалось, клієнт перепідключається із заголовком `Last-Event-ID` і не втрачає подій. Користувач також може скасувати завдання.

**Що зробити** у `solution.py` (стани, події та формат у докстрингу): `JobManager`:
- `submit` із ключем ідемпотентності та лімітом активних завдань на власника;
- перехід станів `queued → running → succeeded | failed | cancelled`, події `status`, `progress`, `result`, `error` з наскрізними `id` в межах завдання;
- прогрес лише вперед, повідомлення без відсотка завжди проходять; запізнілі виклики воркера після скасування ігноруються;
- `events(..., last_event_id)` для відновлення потоку, `get`, `purge` старих завершених завдань;
- `format_sse` і `stream_chunks` (із keepalive для порожніх інтервалів і прапорцем завершення).

**Підказки (без розв'язку):**
- чужий і неіснуючий `job_id` мають поводитись однаково (`KeyError` → 404), інакше можна перебрати чужі id (IDOR, №59);
- SSE-подія це текстові рядки `id:`, `event:`, `data:` і порожній рядок; JSON у `data` має бути в один рядок;
- ліміт активних завдань на власника захищає воркери й бюджет (№133) від одного користувача (CWE-770);
- скасування працює кооперативно: воркер сам дізнається про нього й зупиняє виклик моделі, а менеджер лише фіксує статус.

**Подумай:**
- де в проді жити події: Redis Streams або таблиця в PostgreSQL, щоб кілька інстансів API бачили одне джерело (№116);
- чому для SSE за nginx потрібні `proxy_buffering off` і періодичний keepalive (№67);
- як віддати результат, що не вміщується в подію (посилання на сховище, підписаний URL, №59);
- як поєднати з чергою завдань (ARQ у capstone, №113) і що робити, якщо воркер помер під час `running`.

**Перевірка:** `python check.py t139`. Лише стандартна бібліотека. Далі: додай `POST /jobs`, `GET /jobs/{id}/events` у FastAPI (`StreamingResponse`, `text/event-stream`) і перевір перепідключення `curl -H "Last-Event-ID: 3"`.
