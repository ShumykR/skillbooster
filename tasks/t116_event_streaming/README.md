# №116 · Event streaming у стилі Kafka: партиції, offset, consumer groups 🔴

**Ситуація.** Сервіс замовлень публікує події, а їх читають платежі, склад і аналітика. Кожному споживачу потрібна власна «закладка» в журналі, порядок подій одного замовлення має зберігатись, а коли додається другий екземпляр сервісу, робота повинна поділитись без дублювання. Це вирішують партиції, offsets і consumer groups. Реалізуй їх у мініатюрі, щоб побачити, звідки беруться дублікати й коли подія «зникає».

**Що зробити** у `solution.py` (точні правила в докстрингу):
- `Topic`: партиції, ключ визначає партицію (`crc32`), повідомлення без ключа розподіляються по колу, offset порядковий у межах партиції;
- `ConsumerGroup`: `join`/`leave` з rebalance, `poll` з позицією учасника, `commit`, `seek` (replay), `lag`;
- ключова деталь: після rebalance позиція дорівнює *committed* offset, тож все непідтверджене читається повторно.

**Підказки (без розв'язку):**
- порядок гарантується лише всередині партиції; ключ «замовлення» має завжди потрапляти в одну партицію;
- не плутай позицію (де споживач читатиме далі) і committed offset (що група підтвердила): різниця між ними й дає at-least-once;
- функція `hash()` у Python для рядків різна між запусками (`PYTHONHASHSEED`), тому тут явно `zlib.crc32`;
- lag рахується від committed, а не від позиції: прочитане, але не підтверджене, ще «в боргу».

**Подумай:**
- коли commit краще робити до обробки (at-most-once), а коли після (at-least-once), і як із цим поєднується ідемпотентність (№113);
- чому більше споживачів у групі, ніж партицій, не прискорює обробку, і як обрати кількість партицій наперед;
- чим Kafka відрізняється від RabbitMQ (журнал із replay проти черги, де повідомлення зникає після ack);
- що дають compacted topics, retention та dead-letter topic для «отруйних» повідомлень.
