# №222 · Fitness functions для модульного моноліту 🟡

**Ситуація.** Команда розділила моноліт на модулі `orders`, `billing`, `shared`, але за пів року домен замовлень уже імпортує SQLAlchemy, `billing` лізе в таблиці `orders`, а два модулі залежать одне від одного по колу. Рев'ю цього не ловить: імпорт виглядає невинно. Архітектурні правила мають бути **тестами**, що падають у CI (fitness functions), а не сторінкою у wiki. Це найдешевший спосіб зберегти модульність, поки AI-асистенти щодня дописують «найближчий імпорт, що працює».

**Що зробити** у `analyze` (точні правила в докстрингу): прочитати дерево пакета, побудувати граф імпортів через `ast` (код не виконується) і повернути порушення з ланцюжком імпортів, цикли між модулями та метрики Ca/Ce/нестабільності.

**Підказки (без розв'язку):**
- спершу перетвори кожен файл на «Python-імʼя» і знайди набір внутрішніх модулів: без нього не відрізниш `from shop.billing import api` (імпорт модуля) від `from shop.billing import Invoice` (імпорт імені);
- відносні імпорти треба зробити абсолютними до аналізу; чим пакет файла `__init__.py` відрізняється від пакета звичайного файла?
- заборонений напрямок може бути непрямим: `domain → helpers → sqlalchemy`. Який обхід графа дає найкоротший ланцюжок, і як зробити його детермінованим?
- префікс `shop.orders.domain` не повинен збігатися з `shop.orders.domain_extra`;
- цикли шукай на графі модулів, а не файлів, і вирішуй, що робити з composition root: чому він не повинен бути вершиною цього графа?
