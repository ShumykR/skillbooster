# №111 · URL shortener: коди, аліаси, лічильник кліків, шардування 🟡

**Ситуація.** Класична системна задача, але з реальними граблями: як генерувати короткі коди без колізій, що робити з кастомними аліасами (і з тими, що збігаються з автокодами), чому не можна писати кожен клік у БД окремим `UPDATE`, і як розкласти мільярд посилань по шардах так, щоб додавання вузла не перемішувало все.

**Що зробити** у `solution.py` (точні правила в докстрингу):
- `encode_base62` / `decode_base62` і `normalize_url` (тільки http/https, без логіна й пароля в URL);
- `Shortener`: автокоди з лічильника, дедуплікація, аліаси (формат, зарезервовані імена, `AliasTaken`), TTL;
- `ClickCounter`: пакетний запис кліків у sink без втрат і дублів;
- `ShardRing`: консистентне хешування з віртуальними вузлами.

**Підказки (без розв'язку):**
- код із лічильника не може колідувати з іншим автокодом, але може збігтися з аліасом, тому перевіряй зайнятість;
- `javascript:` та `data:` у короткому посиланні це XSS/фішинг (CWE-601 пов'язане, див. №158), тож схема перевіряється білим списком;
- для кільця зручно тримати відсортований список точок і шукати `bisect`; віртуальні вузли вирівнюють розподіл;
- у консистентному хешуванні при видаленні вузла переїжджають лише його ключі: це перевіряється тестом.

**Подумай:**
- чому послідовні id у base62 відкривають ворогу весь список посилань (перебір) і як це лікується (перестановка бітів, випадкові коди з перевіркою колізій);
- чим 301 відрізняється від 302 для кешування й аналітики;
- де зберігати лічильники при мільйонах кліків на секунду (Redis `INCR` + періодичний скид, Kafka + агрегація);
- як кешувати `resolve` і що робити з кешем при видаленні чи простроченні посилання.

**Перевірка:** `python check.py t111`. Лише стандартна бібліотека. Далі: загорни ядро у FastAPI, додай Redis-кеш для `resolve` і PostgreSQL для сховища, напиши дизайн-документ (оцінка RPS, обсяг сховища, схема шардування).
