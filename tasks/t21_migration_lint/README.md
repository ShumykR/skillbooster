# №21 · Міграції без простою: лінтер 🟡

**Ситуація.** `ALTER TABLE users ADD COLUMN age int NOT NULL` на таблиці з десятками мільйонів рядків або падає (у наявних рядків немає значення), або надовго блокує таблицю, і всі запити застосунку стають у чергу. Безпечний шлях має три кроки: **expand** (додати колонку як NULLABLE), **backfill** (заповнити пакетами), **contract** (додати обмеження без довгого блокування). Помилки такого роду краще ловити *до* запуску міграції, як це роблять squawk і strong_migrations.

**Що зробити** у `solution.py` (правила MIG001–MIG010 у докстрингу): `split_statements` розбиває SQL-скрипт на оператори, `lint_migration` повертає список `(правило, номер оператора)`. Docker і Postgres не потрібні: працюємо з текстом.

**Підказки (без розв'язку):**
- розбивати скрипт по `;` наївно не можна: `;` буває в рядкових літералах, лапкових ідентифікаторах, коментарях і тілах функцій у `$$...$$`. Пиши невеликий посимвольний сканер;
- для правил зручно мати копію оператора, де літерали замінені на заглушку: тоді `DEFAULT 'DROP COLUMN'` не дає хибного спрацювання;
- `ALTER TABLE` має кілька дій через кому, але кома всередині дужок (`CHECK (a IN (1, 2))`, `numeric(10, 2)`) їх не розділяє;
- розрізняй `DROP COLUMN` (небезпечно) та `DROP CONSTRAINT`/`DROP DEFAULT`/`DROP NOT NULL` (ні).

**Подумай:**
- чому `CREATE INDEX CONCURRENTLY` не можна виконувати в транзакції, і що робити, коли інструмент міграцій (Alembic) обертає кожну міграцію в транзакцію;
- схема безпечного `NOT NULL`: додати `CHECK (col IS NOT NULL) NOT VALID` → `VALIDATE CONSTRAINT` → `SET NOT NULL` (у Postgres 12+ він використає перевірений CHECK без повного скану) → прибрати CHECK;
- `lock_timeout` змушує міграцію швидко здатися, а не стояти в черзі й блокувати всіх за собою;
- переіменування колонки робиться в кілька релізів: нова колонка, подвійний запис, перенесення читання, видалення старої.

**Перевірка:** `python check.py t21`. Лише стандартна бібліотека.
