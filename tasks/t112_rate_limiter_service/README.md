# №112 · Rate limiter як сервіс 🟡

**Ситуація.** Один клієнт б'є в API 5000 разів на секунду і кладе всім інстансам БД. Ліміт у памʼяті одного процесу не допоможе: інстансів десять, і кожен «пам'ятає» свою десяту частину. Ліміт мусить жити у спільному сховищі (Redis), працювати атомарно, не ламати API при падінні самого Redis і правильно визначати, хто саме клієнт за ланцюжком проксі.

**Що зробити** у `solution.py` (точні формули в докстрингу):
- `TokenBucket`, `FixedWindow`, `SlidingWindowLog` над спільним `store` (dict замість Redis) з відповіддю `Decision` (залишок, `retry_after`, `reset`);
- `rate_limit_headers`: `RateLimit-*` і `Retry-After`;
- `guarded_allow`: fail-open чи fail-closed, коли Redis недоступний;
- `check_all`: кілька лімітів одночасно (користувач + IP) без «часткового списання»;
- `client_key`: адреса клієнта за `X-Forwarded-For` без довіри до підробних значень.

**Підказки (без розв'язку):**
- час усюди приходить параметром `now`, тому тести детерміновані, а логіка однакова з тією, що ти колись перенесеш у Lua-скрипт Redis;
- token bucket зберігає *пару* (токени, мить останнього оновлення) і дорахує поповнення при наступному запиті, фонових потоків не треба;
- у фіксованого вікна на межі вікон проходить подвійний сплеск: тест це показує навмисно;
- для `check_all` спочатку `peek` усіх, і лише потім `allow`: інакше відмова другого ліміту вже «з'їла» токен першого.

**Подумай:**
- чому перевірка «прочитати лічильник, потім записати» у Redis небезпечна без Lua/`INCR` (гонка між інстансами);
- коли fail-open виправданий (публічний read-API), а коли ні (логін, платіжний ендпоінт, дорогі виклики LLM);
- чому ліміт за IP погано працює за корпоративним NAT, а ліміт лише за користувачем не захищає `/login`;
- що відповідати: 429 з `Retry-After` і єдиним форматом помилки RFC 7807 (№2 з розділу A).
