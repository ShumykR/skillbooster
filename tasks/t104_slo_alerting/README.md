# №104 · Алерти за SLO, а не за CPU 🟡

**Ситуація.** О третій ночі приходить алерт «CPU 91%», а користувачі нічого не помічають. Наступного тижня API п'ять годин повертає 2% помилок, але CPU в нормі, і ніхто не прокинувся. Алерти за ресурсами не повʼязані з болем користувача. Алерти за **швидкістю спалювання error budget** повʼязані: вони питають не «що з сервером», а «чи встигнемо ми дотягнути до кінця місяця в межах SLO».

**Що зробити** у `solution.py` (формули й правила в докстрингу):
- розрахунки бюджету: `error_budget`, `burn_rate`, `budget_consumed`, `hours_to_exhaustion`;
- SLI: `error_ratio`, `latency_sli`, `budget_status` та `release_policy` (що робити з релізами при вичерпанні бюджету);
- `evaluate_alerts`: політика multi-window multi-burn-rate з Google SRE Workbook (швидке спалювання будить людину, повільне створює тікет);
- `alert_expr`: генерація виразу PromQL для правила Prometheus/Grafana.

**Підказки (без розв'язку):**
- burn rate 1 означає «бюджет скінчиться рівно наприкінці вікна»; 14.4 за годину з'їдає 2% місячного бюджету;
- правило потребує *обох* вікон: довге доводить, що проблема суттєва, коротке доводить, що вона триває зараз (інакше алерт дзвонить ще годину після одужання);
- порівняння «більше за factor» суворе; тестуй його на точній межі зі зручними числами (SLO 0.75);
- якщо в `ratios` немає даних для вікна, правило не спрацьовує, а не падає.

**Подумай:**
- чому SLO 100% нереальне й що воно означає для швидкості релізів;
- чому SLI «запити швидше за поріг» кращий за «середню затримку» (звʼязок із histogram із №102);
- де проходить межа між page та ticket і чи варто будити людину алертом, на який нічого робити;
- як виглядає такий алерт у Grafana (JSON-дашборд і Alertmanager) та що показати в сповіщенні (поточний burn rate, залишок бюджету, лінк на дашборд).
