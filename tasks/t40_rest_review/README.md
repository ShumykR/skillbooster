# №40 · REST-рев'ю: лінтер OpenAPI 🟢

**Ситуація.** У команді є API, де `POST /createUser`, `GET /getOrders` з тілом запиту, `DELETE`, що повертає 200 із JSON, і помилки у кожного ендпоінта в різному форматі. Рев'ю такого API вручну повторюється щоразу, тому правила записують у лінтер (на практиці це [Spectral](https://github.com/stoplightio/spectral) або Redocly CLI). Тут ти пишеш мінімальну версію сам: це найкращий спосіб вивчити, що саме вважається хорошим REST-контрактом.

**Що зробити** у `solution.py`: функція `review_openapi(spec)` перевіряє OpenAPI-словник за 11 правилами (R001–R011) і повертає відсортований список унікальних зауважень. Точні визначення («колекція», «сторінка елемента») та формат рядків у докстрингу файлу.

**Підказки (без розв'язку):**
- пройди всі `paths`, для кожного шляху обчисли `segments = path.split("/")`, чи це колекція чи елемент, і лише потім переглядай операції;
- ключі `parameters`, `summary`, `servers` у шляху не є операціями: бери лише з `METHODS`;
- коди відповідей у YAML/JSON бувають і рядками, і числами (`200` проти `"200"`): приведи до `str`;
- `set` для результатів прибирає дублікати, `sorted` дає стабільний порядок.

**Подумай (тести цього не покривають):**
- чому дієслово в URL (`/createUser`) гірше за `POST /users`? Коли дія все ж не вкладається в CRUD (`POST /orders/{id}/cancel`) і як її оформити;
- `PUT` проти `PATCH`, `201` + `Location`, `409` проти `422`, ідемпотентність `PUT`/`DELETE` (завдання №28);
- чому одноманітний формат помилок (RFC 9457, `application/problem+json`, див. завдання №7) важливіший, ніж здається клієнтським розробникам;
- прогін Spectral у CI на кожному PR проти ручного рев'ю: які правила корисні лише як попередження, а які мають блокувати злиття?

**Перевірка:** `python check.py t40`. Спершу тести червоні. Лише стандартна бібліотека.
