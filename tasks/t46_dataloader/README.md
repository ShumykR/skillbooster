# №46 · N+1 у GraphQL/REST і DataLoader 🟡

**Ситуація.** GraphQL-запит `posts { title author { name } }` повертає 50 дописів, і резолвер поля `author` викликається для кожного окремо: 1 запит за дописами і ще 50 за користувачами. Для REST те саме трапляється в серіалізаторах, що звертаються до пов'язаного об'єкта в циклі. На маленькій базі цього не видно, на production запит займає секунди (завдання №22 про N+1 в ORM розглядає той самий клас помилок через SQL).

**Що зробити** у `solution.py`:
1. реалізувати `DataLoader`: збирати всі `load(key)` з одного «тіку» event loop в один пакетний виклик `batch_fn`, дедуплікувати ключі, кешувати, обробляти помилки (повні правила в докстрингу файлу);
2. переписати `posts_with_authors` через нього, щоб для будь-якої кількості дописів було рівно 2 запити до БД.

**Підказки (без розв'язку):**
- «тік» це одна ітерація event loop: перший `load` ставить `loop.call_soon(dispatch)`, а решта `load` з `gather` встигають додати свої ключі, поки dispatch ще в черзі;
- у кеші зручно тримати не значення, а `Future`: тоді другий `load` того ж ключа до завершення пакета просто чекає на той самий `Future`;
- `batch_fn` може кинути виняток, повернути виняток як елемент списку або список не тієї довжини: кожен випадок по-своєму розподіляється між `Future`-ами цього пакета;
- невдалий ключ не повинен лишатись у кеші назавжди.

**Подумай (тести цього не покривають):**
- DataLoader створюють *на запит* (request-scoped), а не глобально: інакше кеш віддасть одному користувачу дані іншого й ніколи не оновиться. Чому глобальний кеш тут небезпечніший, ніж здається?
- пакетування і авторизація: `batch_fn` має застосувати ті самі права, що й одиничний запит, інакше `users_by_ids` віддасть те, що не можна бачити;
- у SQLAlchemy ту саму проблему вирішують `selectinload`/`joinedload` (завдання №22), а в GraphQL (Strawberry, Ariadne, Graphene) DataLoader є стандартним інструментом; коли JOIN кращий за два запити?
- проблема «запит дуже глибокий»: DataLoader лікує кількість запитів, але не складність. Ліміти глибини, складності й persisted queries.
