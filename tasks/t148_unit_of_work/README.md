# №148 · Unit of Work + Repository 🟡

**Ситуація.** Переказ грошей змінює два рахунки й пише аудит. Якщо кожен репозиторій відкриває власне з'єднання і робить власний `commit`, збій посередині лишає списання без зарахування. **Unit of Work** тримає одну транзакцію на всю бізнес-операцію, а репозиторії лише роблять запити в ній.

**Що зробити** у `solution.py` (контракт у докстрингу): `UnitOfWork` як контекстний менеджер, репозиторії `AccountRepo` та `AuditRepo` на спільному з'єднанні та `transfer`, яка виконує переказ атомарно. За замовчуванням усе **відкочується**: зафіксувати треба явно.

**Підказки (без розв'язку):**
- `__exit__` викликається і при винятку, і без нього; рішення «відкотити» не залежить від того, чи був виняток;
- репозиторій не знає про транзакції: він отримує вже відкрите з'єднання;
- значення в SQL передавай параметрами (завдання №146);
- тест перевіряє зафіксований стан через *інше* з'єднання, тож «не зафіксовано» тут означає справді невидимо для інших.

**Подумай (тести цього не покривають):**
- у реальному переказі між читанням балансу і записом клієнт може встигнути змінити рахунок: потрібні блокування чи optimistic locking (завдання №27, №26);
- SQLAlchemy `Session` це вже Unit of Work (+ identity map), а FastAPI-залежність, що видає сесію й робить commit/rollback, найчастіший спосіб його підключити;
- розподіленого UoW між БД і брокером не існує: для цього є Outbox (завдання №29).

**Перевірка:** `python check.py t148`. Вбудований `sqlite3`.
