# №74 · Матриця версій Python, кеш залежностей, паралельні джоби 🟡

**Ситуація.** Пайплайн проходить за 14 хвилин, і всі звикли чекати. Розбір показує: залежності качаються з нуля у кожному job, `lint`, `typecheck` і `test` стоять у черзі один за одним (хоча незалежні), завислий тест тримає runner шість годин, кожен новий push у PR запускає ще одну копію, а старі копії не зупиняються. Економія тут це не оптимізація заради оптимізації: швидкий CI означає, що розробники дійсно його чекають і довіряють.

**Що зробити** у `solution.py`:
1. `audit_ci(text)`: перевірити workflow за 7 правилами (CI001–CI007): немає кешу залежностей, тести без матриці версій, `fail-fast` ховає зламані версії, немає `concurrency` з `cancel-in-progress`, штучна серіалізація перевірок, немає `timeout-minutes`, зайва повна історія git у перевірках;
2. `critical_path(text, minutes)`: за `needs` порахувати час пайплайна як **найдовший ланцюжок**, а не суму: тільки скорочення критичного шляху прискорює пайплайн.

Точні умови правил і формат результату в докстрингу файлу. YAML розбирає `yaml.safe_load` (потрібен `pyyaml`, він у `requirements.txt`).

**Підказки (без розв'язку):**
- `needs` буває рядком або списком, а `with` може бути відсутнім: нормалізуй у допоміжних функціях;
- матриця виглядає як `strategy.matrix.python-version: [...]`; ключ закінчується на `-version`;
- критичний шлях це динамічне програмування по графу з мемоізацією; цикл знаходиться станом «відвідується зараз»;
- не плутай час *job-а* (а матриця його не множить: комбінації йдуть паралельно) з часом усіх комбінацій разом.

**Подумай (тести цього не покривають), і зроби на реальному репозиторії:**
- заміри: у вкладці Actions порівняй тривалість кроків, а не job-ів; кеш `pip`/`uv`/`npm` економить хвилини, але кеш на великих файлах може коштувати довше за завантаження;
- `concurrency` із `group: ${{ github.workflow }}-${{ github.ref }}` скасовує старі запуски PR, але для `main` скасування небезпечне (деплой посередині): умова `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`;
- матриця множить вартість: 3 версії Python × 3 ОС це 9 job-ів; обирай, що справді підтримуєш, і виносьте важку комбінацію на nightly;
- `paths`-фільтри та «запускати лише змінене» (завдання №81), кеш Docker-шарів через `buildx` і `cache-from: type=gha`, self-hosted runner для великих збірок;
- «required checks» і матриці: перейменування job-а в матриці ламає required status check; зручний підхід це один агрегований `gate`-job.
