# №128 · Tool calling: модель викликає ваші функції 🟡 🤖

**Ситуація.** Модель не вміє дізнатись статус замовлення чи курс валют, але вміє *попросити* вас це зробити: повертає ім'я функції та аргументи у вигляді JSON-рядка. Ви виконуєте функцію й повертаєте результат у розмову, після чого модель формулює відповідь. Усе складне тут навколо: модель присилає зіпсований JSON, вигадує інструмент, плутає типи, просить кілька викликів одразу, а інструмент кидає виняток.

**Що зробити** у `solution.py` (формати повідомлень і правила в докстрингу):
- `tool_schemas`: опис інструментів для запиту до моделі;
- `validate_args`: перевірка аргументів за спрощеною JSON-схемою (обовʼязкові, невідомі, типи);
- `run_conversation`: цикл «модель → інструменти → модель» з обмеженням кількості раундів; кожен `tool_call` отримує рівно одне tool-повідомлення, а помилки повертаються моделі як `{"error": ...}`, не валячи цикл.

**Підказки (без розв'язку):**
- API вимагає відповіді на *кожен* `tool_call_id`, навіть помилкову, інакше наступний запит буде відхилено;
- `arguments` приходить рядком: розбирай його сам і не довіряй ні формату, ні типам (`bool` у Python це `int`!);
- модель дивиться на текст помилки й часто самостійно виправляє виклик, тож робіть помилки інформативними;
- довгий результат інструмента з'їдає контекст: обріж його.

**Подумай:**
- які інструменти небезпечно віддавати моделі без перевірки прав користувача (№137, там продовження про авторизацію tool-викликів);
- чому не можна виконувати довільні імена функцій за рядком від моделі (білий список у `by_name`);
- як обмежити вартість циклу (раунди, токени, час) і чим це відрізняється від агента з планом (№135);
- як описати інструмент так, щоб модель обирала його правильно (опис, приклади, чіткі імена).

**Перевірка:** `python check.py t128`. Лише стандартна бібліотека, модель підроблена. Далі: підключи справжню модель з проксі (поле `tools` в OpenAI-форматі) і два реальні інструменти.
