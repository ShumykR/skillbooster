# №154 · Specification: правила, що складаються 🟡

**Ситуація.** Умова «користувач активний, не заблокований і (адмін або власник)» живе в п'яти місцях у п'яти варіантах, з різними помилками. **Specification** робить кожну перевірку іменованим об'єктом, а складні правила збирає з них операторами `&`, `|`, `~`, і ще вміє пояснити, *чому* відмовлено.

**Що зробити** у `solution.py` (докстринг): клас `Spec` з операторами, лінивим обчисленням, метод `failures` (пояснення відмови), декоратор `spec` та `all_of`/`any_of`.

**Підказки (без розв'язку):**
- `__and__`, `__or__`, `__invert__` повертають нові `Spec`; для чужих типів повертай `NotImplemented`, і Python сам видасть `TypeError`;
- `a & b` читається зліва направо: `b` рахуємо лише якщо потрібно;
- `failures` навмисно НЕ ледачий: для пояснення потрібні всі причини, а не перша;
- складене правило зручно представити даними (вид + операнди), а не лише замиканням: тоді з нього можна вивести ім'я й причини.

**Подумай:**
- так само побудовані фільтри ORM: `Q(a) & Q(b)` у Django, `and_`/`or_` у SQLAlchemy; відмінність у тому, що вони будують SQL, а не обчислюють у пам'яті;
- політика авторизації (завдання №52, №137) легко записується таким способом, а `failures` дає змістовну причину відмови для логів (не показуй її клієнту як є);
- перевірка в пам'яті не замінює фільтр у запиті до БД: не завантажуй мільйон рядків заради `spec(row)`.

**Перевірка:** `python check.py t154`. Лише стандартна бібліотека.
