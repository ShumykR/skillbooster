# №6 · Cursor-пагінація 🟡

**Ситуація.** `?page=500&size=20` перетворюється на `OFFSET 10000`: БД читає й викидає 10 000 рядків щоразу, а поки користувач гортає, у стрічку додають нові записи, і сторінки зсуваються (дублі та пропуски). Cursor («продовжити після цього запису») працює за індексом і стабільний.

**Що зробити** у `fetch_page` (контракт у докстрингу): видавати сторінки та курсор за парою `(created_at, id)`. Тест вставляє нові записи між запитами сторінок і вимагає, щоб обхід не дублював і не губив жодного старого запису.

**Подумай:**
- чому однієї колонки `created_at` недостатньо;
- «limit + 1» дозволяє дізнатись про наступну сторінку без `COUNT(*)`;
- для швидкості потрібен індекс на `(created_at, id)` (завдання №23);
- курсор непрозорий для клієнта, щоб формат можна було змінити; підписувати його не обовʼязково, але валідувати треба.

**Перевірка:** `python check.py t06`. Використовується лише вбудований `sqlite3`.
