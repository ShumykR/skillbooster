# №152 · Middleware: ланцюжок обробників 🟡

**Ситуація.** Кожен запит треба залогувати, автентифікувати, порахувати час, обмежити частоту, а помилки перетворити на 500 без стеку. Це **Chain of Responsibility**: кожна ланка вирішує, передати запит далі чи відповісти сама. Так влаштовані ASGI/WSGI-middleware, Express і Django.

**Що зробити** у `build_pipeline` (докстринг): зібрати з `[mw1, mw2, ...]` та кінцевого `handler` одну функцію `request -> response`. Ланка отримує `request` і `call_next`.

**Підказки (без розв'язку):**
- простий спосіб думати про це: рекурсивна функція «виконай ланку з індексом `i`»; `call_next` це замикання на `i + 1`;
- стан одного проходу (чи вже викликали `call_next`) має жити *всередині проходу*, а не в pipeline: інакше другий запит успадкує стан першого;
- за кожну ланку відповідає власний `call_next`;
- порядок: перша ланка зовнішня, тобто ловить помилки всіх наступних.

**Подумай:**
- порядок middleware це частина безпеки: автентифікація має бути *перед* логікою, яку вона захищає, а обмеження частоти *перед* дорогою автентифікацією;
- у Starlette/FastAPI те саме робить `app.add_middleware(...)` (додана пізніше стає зовнішньою); асинхронна версія відрізняється лише `await`;
- чим middleware відрізняється від залежностей FastAPI (`Depends`): запит чи ендпоінт, глобально чи точково.

**Перевірка:** `python check.py t152`. Лише стандартна бібліотека.
