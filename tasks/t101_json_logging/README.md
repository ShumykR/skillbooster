# №101 · Структуровані JSON-логи з correlation id 🟢

**Ситуація.** Користувач скаржиться: «замовлення не пройшло о 14:05». У логах три сервіси, десятки тисяч рядків у вільному форматі, і неясно, який рядок якого запиту. Рішення: кожен запис це один JSON-рядок, а кожен запит має наскрізний `correlation_id`, який повертається клієнту й передається далі.

**Що зробити** у `solution.py` (формат полів і правила в докстрингу):
- `JsonFormatter` перетворює `LogRecord` на один JSON-рядок з полями `ts`, `level`, `service`, `logger`, `message`, `correlation_id`, `extra` і `exc`; чутливі ключі замасковані;
- `bind_correlation_id` та `extract_correlation_id` керують ідентифікатором запиту через `contextvars`;
- `CorrelationMiddleware` це ASGI-обгортка: бере id із `X-Request-ID` (або генерує), виставляє на час запиту, повертає у відповіді.

**Підказки (без розв'язку):**
- `contextvars` (а не глобальна змінна чи `threading.local`) коректно працює з `async`: кожна задача бачить своє значення;
- `ContextVar.set` повертає токен, яким значення відновлюють через `reset`; робити це треба в `finally`;
- чужий заголовок це недовірений ввід: символ нового рядка в `X-Request-ID` без перевірки дозволив би підробити рядок логу (CWE-117), хоча JSON-формат вже екранує переноси в самому записі;
- стандартні атрибути `LogRecord` легко відфільтрувати, створивши порожній запис і взявши його `__dict__`.

**Подумай:**
- чому не логувати тіла запитів і заголовки цілком, і де проходить межа між «корисно для налагодження» та «витік даних» (GDPR, №62);
- як передати той самий id у виклики інших сервісів і в задачі воркера (черга, №88);
- чим correlation id відрізняється від `trace_id` OpenTelemetry (№103) і чому їх часто збігають;
- як змусити `uvicorn` і сторонні бібліотеки писати в тому самому JSON-форматі (`dictConfig`).

**Перевірка:** `python check.py t101`. Лише стандартна бібліотека (ASGI-сервер не потрібен: тести викликають middleware напряму).
