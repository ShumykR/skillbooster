# №89 · Secrets Manager / Parameter Store замість змінних у коді 🟡

**Ситуація.** Пароль до бази спочатку жив у коді, потім у `.env` у репозиторії, потім у змінних середовища ECS. Ротація раз на рік означає редеплой усіх сервісів і «а раптом я забув один». Правильний шлях: секрети лежать у Secrets Manager (або Parameter Store), сервіс забирає їх при старті й періодично оновлює, а ротація відбувається без редеплою. Але наївний `get_secret_value()` на кожен запит це затримка, гроші й тротлінг, а кеш без ротації ламається у день зміни пароля.

**Що зробити** у `solution.py`: `SecretsClient` із кешем за TTL (з розкидом), stale-if-error при збоях, правильним поводженням при ротації (`call_with_secret`: свіже значення, потім `AWSPREVIOUS`) і безпечним поданням. Правила в докстрингу файлу. Мок `fetch` змодельовано як справжній `GetSecretValue` із стадіями `AWSCURRENT` та `AWSPREVIOUS`.

**Підказки (без розв'язку):**
- у запису кешу тримай не лише значення, а й момент отримання та вже обчислений TTL: тоді розкид (`jitter`) застосовується один раз;
- відрізняй три випадки при оновленні: все гаразд, тимчасовий збій (віддай старе, якщо воно не надто старе) і «секрету немає» (це не збій, а факт: нічого не кешуй);
- ротація проходить у кілька кроків, і є вікно, коли в Secrets Manager вже новий пароль, а в БД ще старий: у цей момент `AWSPREVIOUS` рятує сервіс;
- `__repr__` має показувати лише імена (щоб `print(client)` чи лог винятку не виніс пароль).

**Подумай (тести цього не покривають), і зроби руками:**
- Secrets Manager (платний, є вбудована ротація для RDS через Lambda, версіонування, міжакаунтний доступ) проти Parameter Store `SecureString` (безкоштовний стандартний рівень, простіший, без вбудованої ротації): що обрати для чого; в обох секрет шифрується KMS, і право `kms:Decrypt` теж частина доступу;
- IAM: ролі сервісу дають `secretsmanager:GetSecretValue` лише на конкретний ARN (завдання №60), а не на `*`;
- у ECS секрети можна підставити як змінні контейнера (`secrets` у task definition), але тоді оновлення вимагає перезапуску; бібліотека AWS (`aws-secretsmanager-caching`) чи sidecar/Lambda extension робить кеш замість тебе;
- секрети не повинні потрапляти в логи, звіти про помилки (Sentry), `docker inspect`, артефакти CI: перевір себе сканером з завдання №54 і історією git (`git log -S`);
- якщо секрет уже потрапив у git: його вважають скомпрометованим, видалення з історії не достатньо, потрібна ротація.
