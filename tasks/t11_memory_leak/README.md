# №11 · Memory leak 🔴

**Ситуація.** Сервіс мініатюр працює добу, і RSS росте рівно, без піків, аж до OOM-kill. Перезапуск «лікує», тож у production це маскують рестартами, поки не знайдуть витік. Тут витоків кілька, і виправлення одного не видно за іншим.

**Що зробити** у `solution.py`: знайти, що саме утримує пам'ять після кожного запиту, і виправити, не змінюючи поведінки (докстринг файлу: спільний кеш за `(user_id, size)`, обмежений LRU, без підписок на шині після запиту).

**Як шукати (це і є навичка):**
1. Запусти цикл із тисяч викликів `handle` і зніми `tracemalloc` до/після: `tracemalloc.start()`, `snapshot()`, `snapshot2.compare_to(snapshot1, "lineno")`. Рядки з найбільшим приростом і є підозрювані;
2. для «хто тримає цей об'єкт» використай `gc.get_referrers(obj)` або `objgraph`/`memray` у реальному проєкті;
3. питання до кожного підозрюваного: чи росте *кількість* утримуваних об'єктів разом із кількістю запитів?

**Підказки (без розв'язку):**
- ключ кешу, що містить унікальний ідентифікатор запиту, ніколи не потрапляє в кеш двічі: це не кеш, а склад;
- функція, створена всередині обробника (closure), утримує все, на що посилається; хто утримує саму функцію?
- пара «підписатись / відписатись» має бути в `try/finally`: відписка не повинна залежати від того, чи обробник кинув виняток;
- `collections.OrderedDict` + `move_to_end` або `functools.lru_cache` для обмеженого кешу.

**Подумай (тести цього не покривають):**
- глобальні кеші, реєстри обробників, `lru_cache` без `maxsize`, списки в модулі, `logging.Handler` без зняття, фонові задачі, що ніколи не завершуються: типові джерела витоків у Python-сервісах;
- як відрізнити витік від фрагментації пам'яті або від кешу, що просто «прогрівається»? Графік RSS після виходу на плато;
- у production: метрика `process_resident_memory_bytes`, ліміти пам'яті в контейнері й алерт на тренд, а не на поріг.

**Перевірка:** `python check.py t11`. Спершу тести червоні. Тест порівнює пам'ять Python (tracemalloc) між 500-м і 3500-м запитами; виправлення лише одного з витоків його не проходить.
