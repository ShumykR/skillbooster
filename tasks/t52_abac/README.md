# №52 · RBAC → ABAC 🟡

**Ситуація.** Спочатку вистачало ролей (`admin`, `editor`). Потім з'явились клієнти (tenants), «чужі» ресурси, секретні документи та архів. Ролі самі по собі вже не відповідають на питання «чи може *цей* користувач зробити *це* з *цим* ресурсом», тому дозволи тепер залежать від атрибутів користувача, ресурсу та контексту (ABAC). Класична вразливість тут це IDOR / broken access control, номер 1 в OWASP Top 10.

**Що зробити** у `authorize` (політика у докстрингу): поєднати дозволи ролей і власника з забороною за tenant, рівнем доступу та статусом ресурсу. Заборони сильніші за дозволи.

**Подумай:**
- чому default deny безпечніший за список заборон;
- політики краще тримати окремо від коду застосунку (OPA/Rego, Cedar, Casbin), а в коді мати одну точку перевірки;
- перевірка на рівні списку: не повертай ресурси, до яких немає `read`, а не відфільтровуй у UI.

**Перевірка:** `python check.py t52`.
