# №134 · Надійність LLM-викликів: ретраї, 429, circuit breaker, резервний провайдер 🟡 🤖

**Ситуація.** Провайдер моделі періодично відповідає 429 («занадто часто»), 529 («перевантажено»), зависає або віддає 500. Один виклик без захисту дає користувачу помилку. Простий ретрай у циклі без пауз добиває провайдера. А якщо провайдер лежить годину, кожен запит чекає таймаут. Потрібен роутер: повторює те, що варто повторити, вчасно переходить до резервного провайдера, перестає стукати в мертвого і не виходить за загальний бюджет часу.

**Що зробити** у `solution.py` (правила класифікації та порядок кроків у докстрингу): клас `ProviderRouter.call`:
- класифікація: повторювані (429, 5xx, таймаут, обрив зʼєднання), помилка авторизації (до наступного провайдера), «запит відхилено» (400/404/413/422: не повторювати і не переходити, бо те саме відбудеться скрізь);
- ретраї з експоненційною паузою або `Retry-After` від провайдера; паузу, що не вміщується в загальний `deadline`, не чекаємо;
- circuit breaker на кожного провайдера (closed → open → half-open) із однією пробною спробою;
- журнал спроб `attempts`, зручний для логів і метрик.

**Підказки (без розв'язку):**
- бюджет часу рахується від початку виклику, а не від початку кожної спроби; його перевіряють перед кожною спробою і перед сном;
- у стані half-open пробна спроба одна: якщо вона невдала, breaker відкривається знову на повний період;
- помилку «відхилено» не рахуй у breaker: це вина запиту, а не провайдера;
- невідомі винятки (наприклад, `ValueError` з вашого коду) не ховай: їх треба бачити як баги.

**Подумай:**
- чому ретраї без jitter створюють «громовий натовп», коли тисяча клієнтів повторює запит одночасно (№42, №43);
- як порівняти відповіді різних провайдерів (різні моделі дають різні тексти) і чи варто мати резервного провайдера з тією самою моделлю;
- чому streaming ускладнює ретраї (пів відповіді вже показано користувачу);
- які метрики потрібні для моніторингу: частка fallback, стан breaker, p95 за провайдером (№102, №140).
