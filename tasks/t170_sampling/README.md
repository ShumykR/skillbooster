# №170 · Sampling: temperature, top-k, top-p, logprobs 🟢

**Ситуація.** Одна й та сама модель на одному промпті то відповідає однаково, то різно, а в API є незрозумілі `temperature`, `top_p` і `logprobs`. Усе це один крок: з вектора logits обирається наступний токен. Поки ти не реалізував його сам, «температура 0 це детермінізм» чи «top-p та top-k не одне й те саме» залишаються вірою, а не знанням. Це база для оцінки якості (evals) і для відтворюваності відповідей у production.

**Що зробити** у `solution.py` (точні правила в докстрингу):
- `softmax`, `log_softmax`: стійкі до великих значень, з температурою;
- `filter_top_k`, `filter_top_p`: відсікання «хвоста» з перенормуванням;
- `sample`: повний крок з одним викликом `rng.random()`, greedy при `temperature=0`, logprob обраного токена.

**Підказки (без розв'язку):**
- що станеться з `exp(1000)`? Яку величину можна відняти від усіх logits, щоб результат не змінився?
- температуру застосовують до logits **до** softmax; чому «підняти до степеня після» дає те саме, а чому це гірше числово?
- «найкоротший префікс із сумою ≥ p» і «усі токени з ймовірністю > p» це різні речі: який із них nucleus?
- після фільтра сума ймовірностей уже не 1: що станеться з вибором за `u`, якщо не перенормувати?
- нічия в `argmax` і в top-k вирішується за індексом: чому відтворюваність важливіша за «справедливість»?
- logprob, який повертають API, береться з розподілу до фільтрів: чим це корисно для оцінки впевненості моделі?

**Подумай:**
- чому навіть при `temperature=0` провайдери не гарантують побітово однакових відповідей (паралельні reduce на GPU, батчинг, зміни версії моделі) і що з цього випливає для evals (завдання №191–194)?
- які налаштування обирати для класифікації, витягання JSON, генерації ідей? Чому змінювати одночасно `temperature` і `top_p` не рекомендують?
- для чого потрібні logprobs у RAG: поріг «не знаю», калібрування впевненості, виявлення вигаданих цитат?
