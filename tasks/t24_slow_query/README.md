# №24 · Повільний запит: від 8 секунд до мілісекунд 🔴

**Ситуація.** Дашборд показує «20 останніх оплачених замовлень клієнтів країни X, починаючи з дати Y». На тестовій базі працює миттєво, на production із мільйонами рядків займає секунди. Запит правильний, але повільний: він читає всю таблицю, обчислює функцію для кожного рядка й сортує результат, щоб віддати лише двадцять.

**Що зробити** у `solution.py`: змінити `QUERY` (результат має лишитись *точно таким самим*) і додати до `INDEXES` не більше двох `CREATE INDEX`. Тести порівнюють результат з незалежним розрахунком у Python, а швидкість міряють **кроками SQLite VM** (`set_progress_handler`), а не секундами, тож перевірка детермінована. Заглушка правильна, але повільна: на ній падають лише перевірки швидкості й плану.

**Підказки (без розв'язку):**
- відкрий `EXPLAIN QUERY PLAN` для заглушки: шукай `SCAN`, `TEMP B-TREE` та пояснення, чому індекс не міг би допомогти навіть якби він був;
- функція від колонки в `WHERE` (`date(col)`) не дає використати індекс по цій колонці; порівняння тексту дат із початком дня можна записати без функції;
- порядок колонок у складеному індексі: спершу рівність, потім діапазон/сортування; індекс, що вже віддає рядки у потрібному порядку, скасовує сортування;
- перевіряй кожну зміну окремо (лише запит; лише індекс; обидва): так видно, що саме дало виграш.

**Подумай:**
- у PostgreSQL те саме робиться через `EXPLAIN (ANALYZE, BUFFERS)`; шукай `Seq Scan`, `Sort`, різницю між оцінкою (`rows=`) й фактом (`actual rows`);
- чим небезпечна пагінація через `OFFSET 100000` (рядки все одно читаються й відкидаються) і що таке keyset-пагінація (завдання №6);
- індекси прискорюють читання й сповільнюють запис та займають місце, тому їх обмежено: «додати індекс на всі колонки» не рішення;
- `pg_stat_statements` і `auto_explain` показують, *які* запити взагалі варто оптимізувати.
