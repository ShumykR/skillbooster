# №86 · RDS: ревʼю конфігурації і бюджет зʼєднань 🟡

**Ситуація.** База піднята «як за туторіалом»: один інстанс без Multi-AZ, бекапи на 1 день, публічний доступ, SSL не примусовий. Вона працює, доки не станеться перша проблема. А ще проста арифметика: 10 реплік API по 20 зʼєднань у пулі це 200 зʼєднань, тоді як `db.t3.micro` має близько сотні. У пікову хвилину застосунок отримає `too many connections`.

**Що зробити** у `solution.py` (правила RDS001–RDS009 у докстрингу):
- `review_rds` перевіряє конфігурацію інстансу (формат `describe-db-instances`), правила security group і параметри TLS та логування, по-різному для prod і dev;
- `connection_budget` рахує, чи вміщаються пули всіх сервісів у `max_connections` (з запасом на rolling update);
- `default_max_connections` дає типовий ліміт зʼєднань RDS PostgreSQL за обсягом памʼяті інстансу.

**Підказки (без розв'язку):**
- відсутній ключ у відповіді AWS це не помилка: `db.get(...)`, а `True` перевіряй явно (`is True`);
- у «відкрито на весь світ» входять і IPv4, і IPv6; `0.0.0.0/8` чи `0.0.0.0/1` це не те саме, що `0.0.0.0/0`;
- у `connection_budget` округлюй кількість реплік вгору *для кожного сервісу окремо* і не користуйся дробами.

**Подумай:**
- Multi-AZ це про доступність (автоматичний failover), а *не* про бекапи й не про читання з репліки; Read Replica це інший інструмент;
- пул на стороні застосунку (SQLAlchemy `pool_size` + `max_overflow`) і зовнішній пулер (RDS Proxy, PgBouncer) вирішують проблему різними способами; для serverless пулер майже обовʼязковий;
- доступ до бази лише з приватних підмереж і лише від security group застосунку (`{"sg": "sg-app"}`), а не за CIDR;
- відновлення з бекапу створює *новий* інстанс (див. №33), тож потренуй це заздалегідь.

**Перевірка:** `python check.py t86`. Лише стандартна бібліотека, AWS не потрібен. Далі: `aws rds describe-db-instances --query 'DBInstances[0]'` на власній базі й прогін функції на результаті.
