# №72 · Контейнер «падає»: діагностика 🔴

**Ситуація.** Pod у статусі `CrashLoopBackOff`: це лише симптом, причин може бути десяток. Закінчилась памʼять (`OOMKilled`, код 137), у `ENTRYPOINT` помилка в шляху (код 127), порт зайнятий, немає змінної середовища, процес відпрацював і вийшов із кодом 0, а kubelet його перезапускає. Досвідчений інженер дивиться на `reason`, код виходу, події та хвіст логу і знає, куди рити далі. Ти запишеш цю логіку кодом.

**Що зробити** у `solution.py` (таблиця правил та їх порядок у докстрингу):
- `diagnose` повертає один вердикт за станом контейнера;
- `crashloop_backoff` рахує паузу перед наступним перезапуском;
- `recommend_memory_limit` пропонує ліміт памʼяті за вибіркою піків, щоб OOM не повторився.

**Підказки (без розв'язку):**
- порядок перевірок важливий: код 137 без доказів тиску на памʼять це «когось вбили», а не OOM;
- liveness-проба вбиває контейнер SIGTERM/SIGKILL, тому без подій у `events` це легко сплутати з OOM;
- код виходу 0 при `restart_policy: Always` теж проблема: контейнер не тримає foreground-процес;
- у `recommend_memory_limit` уникай дробів: множ і ділися цілими, округлення вгору робиться через `-(-a // b)`.

**Подумай:**
- `kubectl describe pod` (Events, Last State), `kubectl logs --previous` (логи *минулого* запуску, а не поточного) і `kubectl debug` з ephemeral-контейнером: твоя «стандартна трійка»;
- limit памʼяті в Kubernetes жорсткий (OOM), а limit CPU лише гальмує (throttling), тому їх підбирають по-різному;
- для Python: кілька воркерів `uvicorn`/`gunicorn` множать споживання, а ліміт контейнера порахований на *весь* контейнер;
- дві причини з різними симптомами: `exec format error` майже завжди означає образ, зібраний під іншу архітектуру (arm64 на Mac, amd64 у кластері).
