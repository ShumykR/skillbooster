# №78 · OIDC до AWS замість довгоживучих ключів 🟡

**Ситуація.** У секретах GitHub лежать `AWS_ACCESS_KEY_ID` та `AWS_SECRET_ACCESS_KEY` від IAM-користувача з правами на деплой. Такий ключ не спливає, його скопіювали в три форки й один раз надрукували в логах. Сучасний шлях це OIDC: workflow отримує від GitHub короткоживучий токен, обмінює його на роль AWS і діє лише хвилини. Але вся безпека такого обміну тримається на одному місці, **trust policy ролі**. Якщо там не вказано, *чиї* токени довіряються, роль може отримати будь-який репозиторій на GitHub (типова помилка з копіпасти з туторіалів).

**Що зробити** у `solution.py`: `audit_trust_policy(policy, repo)` перевіряє trust policy за семи правилами (OIDC001–OIDC007): відсутність умови на `sub`, відсутній чи чужий `aud`, чужий репозиторій, організація-цілком (`repo:acme/*`), надто широкий суфікс (будь-яка гілка, `pull_request`), не той `Action`, `Principal: "*"`. Точні умови в докстрингу файлу.

**Підказки (без розв'язку):**
- умова `sub` має вигляд `repo:OWNER/NAME:ref:refs/heads/main` або `repo:OWNER/NAME:environment:production`: розбирай на частини, а не регулярним виразом «усе в одному»;
- ключі умов бувають в `StringEquals` і в `StringLike`, а значення рядком або списком: спершу все нормалізуй;
- спочатку відсій statement-и, що стосуються саме GitHub-провайдера (за кінцівкою ARN), інакше будуть хибні спрацювання на ролях для ECS/SAML;
- не плутай «інший репозиторій» (OIDC003, явна помилка) і «шаблон на кілька» (OIDC002).

**Подумай (тести цього не покривають), і зроби руками:**
- налаштування в AWS: `aws iam create-open-id-connect-provider --url https://token.actions.githubusercontent.com --client-id-list sts.amazonaws.com`; у workflow `permissions: id-token: write` і крок `aws-actions/configure-aws-credentials` з `role-to-assume` (без жодних `AWS_SECRET_ACCESS_KEY`: перевірку цього дає аналізатор workflow із завдання №73);
- чому `pull_request` у `sub` небезпечний для ролі деплою: код з PR (навіть з вашого репозиторію) виконується з правами ролі; для PR роблять окрему роль тільки на читання;
- `environment:production` + обовʼязкове схвалення в GitHub Environments дає **ручний шлюз** перед отриманням ролі (завдання №76);
- кастомні claims (`job_workflow_ref`) дозволяють обмежити роль конкретним reusable workflow: сильніше, ніж лише репозиторій;
- ті самі принципи для GitLab CI, Terraform Cloud, Kubernetes (IRSA/Pod Identity): ідентичність робочого навантаження замість секрету, а права ролі мінімальні (завдання №60).

**Перевірка:** `python check.py t78`. Спершу тести червоні. Лише стандартна бібліотека, AWS не потрібен.
