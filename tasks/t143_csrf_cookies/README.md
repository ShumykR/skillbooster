# №143 · CSRF і прапорці cookie 🟡

**Ситуація.** Користувач залогінений у вашому застосунку, відкриває чужу сторінку, і та непомітно відправляє `POST /transfer` від його імені: браузер сам додає cookie сесії. CSRF це CWE-352, **№3 у MITRE CWE Top 25**. Атаку відпрацюй на лабах [PortSwigger (CSRF)](https://portswigger.net/web-security/csrf), а тут напиши захист.

**Що зробити** (правила в докстрингу):
1. `audit_set_cookie`: розібрати `Set-Cookie` і знайти відсутні `Secure`, `HttpOnly`, `SameSite`, хибні префікси `__Host-`/`__Secure-` та надто довге життя;
2. `CsrfGuard`: токен, прив'язаний до сесії через HMAC, плюс перевірка `Origin`/`Referer`, плюс строк життя. Годинник передається ззовні, тому тести детерміновані.

**Корисно знати:**
- `SameSite=Lax` у сучасних браузерах за замовчуванням закриває більшість CSRF, але це не заміна токену: захист не покриває піддомени, старі браузери та GET, що змінюють стан;
- якщо автентифікація йде заголовком `Authorization: Bearer ...`, CSRF неможливий: браузер сам такий заголовок не додає. CSRF-токен потрібен для cookie-сесій, а не для API з токенами;
- «synchronizer token» і «double-submit cookie» це два способи тримати токен; HMAC-варіант тут не потребує сховища на сервері;
- `HttpOnly` не рятує від CSRF, але ускладнює крадіжку cookie при XSS (завдання №142).
