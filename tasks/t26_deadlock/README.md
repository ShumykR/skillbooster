# №26 · Deadlock 🔴

**Ситуація.** Переказ грошей блокує рахунок-відправник, потім рахунок-отримувач. Двоє людей одночасно переказують один одному, і кожна транзакція тримає один рахунок та чекає на другий. Postgres помітить цикл через секунду (`deadlock_timeout`) і вб'є одну з транзакцій з помилкою `deadlock detected`, але користувач отримає 500.

**Що зробити** у двох функціях (докстринг): знайти учасників deadlock у графі очікування та виправити причину єдиним порядком блокувань. Тест перебирає **усі можливі чергування** кроків двох-трьох транзакцій: у початковому плані deadlock досяжний, у впорядкованому ні.

**Корисно знати:**
- універсальне лікування: усі транзакції беруть ресурси в одному порядку (наприклад, `ORDER BY id`: `SELECT ... FOR UPDATE` двох рахунків спочатку з меншим id);
- додаткові захисти: короткі транзакції, `lock_timeout`, повтор транзакції після `deadlock detected` (SQLSTATE `40P01`), `SELECT ... FOR UPDATE SKIP LOCKED` для черг;
- у логах Postgres повна картина deadlock'у (хто кого чекав); у MySQL `SHOW ENGINE INNODB STATUS`;
- «100 паралельних транзакцій» з каталогу можна перевірити справжнім Postgres і `asyncio.gather`; тут алгоритм винесено в чисту модель, щоб тест був детермінований.

**Перевірка:** `python check.py t26`.
