# №131 · Evals: регресійні тести для промптів 🔴 🤖

**Ситуація.** Ви «покращили» системний промпт, і два демо-приклади стали виглядати краще. А що з рештою двохсот питань користувачів? Без еталонного набору та автоматичних перевірок кожна зміна промпту, моделі чи параметрів це лотерея. Eval це юніт-тести для LLM: набір кейсів, перевірки відповідей і гейт у CI, який не пускає зміну, що щось зламала.

**Що зробити** у `solution.py` (формат кейсів і мітки в докстрингу):
- `grade`: перевірки `exact`, `contains`, `not_contains`, `regex`, `max_chars`, `json` (за шляхом, з огорожею ```json) і `judge` (LLM-as-judge: оцінка 1–5 за критерієм);
- `run_eval`: прогін кейсів із повторами для нестабільних моделей і порогом проходження, підсумок за тегами; виняток моделі валить кейс, а не весь запуск;
- `compare_runs`: порівняння з базовим запуском: нові регресії, виправлені кейси, зміна pass rate і підсумковий `ok` для CI.

**Підказки (без розв'язку):**
- детерміновані перевірки (regex, json, заборонені фрази) дешеві й надійні, судді-LLM лишай для того, що інакше не перевіриш (корисність, тон);
- відповідь судді це недовірений текст: шукай `SCORE: n` регулярним виразом і відрізняй «суддя поставив 2» від «суддя взагалі не відповів за форматом»;
- регресія важливіша за середній pass rate: загальний відсоток міг зрости, а клієнтський кейс зламатись;
- для нестабільних відповідей пробуй `repeats` і `pass_threshold`, але не ховай за ними справжню нестабільність.
