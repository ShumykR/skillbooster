# №29 · Outbox pattern 🔴

**Ситуація.** Сервіс замовлень пише в БД, а потім відправляє подію в брокер. Процес упав між цими кроками: клієнт заплатив, а склад про замовлення не дізнався. Розподіленої транзакції БД+брокер не існує.

**Що зробити:**
1. `place_order`: запис замовлення й запис у `outbox` в **одній транзакції** (падіння посередині не лишає нічого).
2. `relay`: читає непослані події по порядку, публікує, ставить `sent_at`. Якщо брокер недоступний, зупиняється й піднімає помилку; наступний запуск продовжує з того ж місця.

Доставка тут **at-least-once**: подія може піти двічі (упали між `publish` і `sent_at`), тому споживач дедуплікує за стабільним `event_id`.

**Перевірка:** `python check.py t29`

**У production:** `relay` це окремий процес (або Debezium/CDC), а `FOR UPDATE SKIP LOCKED` дає змогу запускати кілька інстансів.
