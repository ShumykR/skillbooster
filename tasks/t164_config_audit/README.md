# №164 · Аудит конфігурації за середовищем 🟡

**Ситуація.** У production лишився `debug=True`: помилка показує трасування стеку зі шляхами й змінними, а інтерактивний відлагоджувач дозволяє виконати код. `/docs` розкриває всю схему API, `CORS: *` дозволяє будь-якому сайту читати відповіді, а `SECRET_KEY=changeme` дає підробляти сесії. Це не помилки коду, а помилки *конфігурації*: CWE-489 (активний код відладки) і категорія A02 Security Misconfiguration.

**Що зробити** у `audit_settings` (правила CFG001–CFG010 у докстрингу): отримати назву середовища та словник налаштувань і повернути список ідентифікаторів порушених правил. У `dev` усе дозволено, у `prod`/`staging` діють суворі правила.

**Підказки (без розв'язку):**
- значення зі змінних оточення — це *рядки*: `"False"` істинне для `bool("False")`! Для булевих налаштувань напиши окремий розбір;
- «fail closed»: для налаштувань безпеки (хости, секрет, прапорці cookie) відсутнє значення це порушення, бо за замовчуванням воно, як правило, небезпечне; а для «небезпечних» опцій (`debug`) відсутність нормальна;
- URL бази розбирай через `urllib.parse.urlsplit`: пароль може бути percent-закодований, а `sslmode` лежить у query-частині;
- порівнюй регістронезалежно там, де про це сказано, і не падай на несподіваних типах.

**Подумай:**
- конфігурацію краще мати одним типізованим об'єктом (`pydantic-settings`, завдання №1), де валідатор *на старті* відмовляється запускати production з небезпечними значеннями (fail fast);
- секрети беруться зі сховища (AWS Secrets Manager, Vault), а не з файлу в репозиторії; перевірка довжини ключа не доводить, що він справді випадковий;
- ті самі ідеї для інфраструктури вже були в завданнях №71 (compose), №84 (Terraform), №93 (Kubernetes);
- такий аудит запускай у CI проти *реальних* значень production (без секретів) і при кожному деплої.

**Перевірка:** `python check.py t164`. Лише стандартна бібліотека.
