# №15 · SSE-брокер: реконект і backpressure 🟡

**Ситуація.** Додаток показує живі сповіщення через Server-Sent Events. Мобільний клієнт заходить у ліфт, з'єднання рветься, браузер сам перепідключається і надсилає `Last-Event-ID`. Сервер має повторити пропущене. Інший клієнт сидить на поганому Wi-Fi і читає повільніше, ніж ти публікуєш: якщо тримати для нього необмежену чергу, пам'ять сервера росте, поки не впаде процес (CWE-770).

**Що зробити** у `solution.py`: брокер подій у пам'яті з історією для повтору і обмеженими чергами, плюс `format_sse` та `heartbeat`. Точні правила (повтор, `needs_resync`, закриття повільних) у докстрингу файлу. Мережі, потоків і asyncio тут немає: усе перевіряється детерміновано викликами методів.

**Підказки (без розв'язку):**
- історія це `collections.deque(maxlen=history)`; черга підписника теж `deque`, але з перевіркою довжини *до* додавання;
- «пропущено щось, чого вже немає» перевіряється порівнянням `last_event_id + 1` з id найстарішої події в історії;
- закриття повільного підписника відбувається в `publish` і не кидає виняток: publisher не повинен залежати від клієнта;
- у `format_sse` поділ `data` робиться `splitlines()`: тоді `\r` і `\n` у даних не можуть створити нове поле.

**Подумай (тести цього не покривають):**
- «закрити повільного» чи «викинути найстаріше з його черги»? Який вибір підходить для чату, а який для лічильника на дашборді? Чому для SSE з `id:` закриття + реконект з `Last-Event-ID` часто чесніше за мовчазну втрату?
- клієнт перепідключається сам, а за браузером ти не керуєш: затримку між спробами сервер може підказати полем `retry: 3000`;
- на кількох інстансах сервера `Last-Event-ID` потребує спільного джерела порядку (Redis Streams, Postgres + LISTEN/NOTIFY): історія в пам'яті одного процесу після деплою зникає;
- проксі та балансувальники закривають «тихі» з'єднання: тому `heartbeat` і заголовки `Cache-Control: no-cache`, `X-Accel-Buffering: no`.
