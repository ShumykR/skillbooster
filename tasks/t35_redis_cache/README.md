# №35 · Redis-кеш: cache-aside 🟡

**Ситуація.** Сторінка профілю б'є в Postgres на кожен перегляд, база ледве дихає. Кеш у Redis знімає 95% навантаження, але приносить дві складнощі: як не віддавати застарілі дані та що робити, коли сам Redis упав.

**Що зробити** у `UserService` (контракт у докстрингу): читання через кеш, негативне кешування, інвалідація після запису і відмовостійкість до `CacheError`. Тести рахують звернення до БД і перевіряють порядок викликів.

**Подумай:**
- TTL це страховка від забутої інвалідації, а не заміна їй;
- cache stampede: коли популярний ключ протух, сотні запитів одночасно йдуть у БД (завдання №36 «single-flight»; ще допомагає випадковий розкид TTL ±10%);
- кеш зберігає рядки: dict, `datetime` та `Decimal` треба явно серіалізувати;
- ключі версіонують (`user:v2:{id}`), щоб зміна формату не віддавала старі структури;
- Redis це кеш, а не джерело правди: додаток має працювати без нього, хай і повільніше.

**Перевірка:** `python check.py t35`. Redis не потрібен, тести використовують імітацію.

**Далі:** підключи справжній Redis (`docker run -p 6379:6379 redis:7`) і бібліотеку `redis-py`, виміряй затримку з кешем і без.
