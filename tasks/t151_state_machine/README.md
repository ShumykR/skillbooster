# №151 · State: життєвий цикл як таблиця 🟡

**Ситуація.** Статус замовлення змінюють у десяти місцях: `order.status = "shipped"` без перевірки, чи було воно оплачене. Через рік виявляється, що частину відвантажили без оплати, а «видалені» замовлення повертаються до життя. **State machine** робить допустимі переходи даними, які можна прочитати, перевірити й протестувати.

**Що зробити** у `solution.py` (докстринг): `StateMachine` з охоронцями (`guards`) і хуком, а також `analyze`, яка шукає дефекти самої таблиці: недосяжні й кінцеві стани.

**Підказки (без розв'язку):**
- таблиця `{(стан, подія): новий_стан}` природно захищає від неоднозначності: у ключа один результат;
- відмова не повинна лишати слідів: ні нового стану, ні запису в історію;
- `history` як властивість повертає копію, інакше її зіпсує зовнішній код;
- `analyze`: пошук у ширину/глибину від початкового стану.

**Подумай:**
- в БД стан зберігають рядком + `CHECK`, а перехід роблять умовним оновленням `UPDATE ... SET status = 'shipped' WHERE id = ? AND status = 'paid'`: інакше два паралельні запити обійдуть автомат (№27);
- хук викликається після зміни стану; що б змінилось, якби перед (і при помилці хука стан відкочувався)?
- для великих автоматів дивись бібліотеки `transitions` та `python-statemachine`; ідею вони реалізують ту саму.

**Перевірка:** `python check.py t151`. Лише стандартна бібліотека.
