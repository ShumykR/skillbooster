# №166 · Скидання пароля 🟡

**Ситуація.** «Забули пароль?» це другий вхід у систему, і його зламують частіше, ніж сам логін. Типові дірки: відповідь «такого email немає» (перебір користувачів), токен із `user_id + час` (передбачуваний), токен без терміну життя або багаторазовий, старе посилання працює після нового запиту, токен лежить у базі як є (витік бази = захоплення акаунтів).

**Що зробити** у `solution.py` (контракт у докстрингу): клас `ResetService` з `request_reset(email)` і `confirm_reset(token, new_password)`. Час, відправка листа, зміна пароля й джерело токенів передаються ззовні, тому тести детерміновані й жодної пошти немає.

**Підказки (без розв'язку):**
- сервісу не потрібен сам токен після відправки: достатньо його хешу (швидкого SHA-256, бо токен випадковий і довгий; повільні KDF потрібні для паролів, а не для токенів із 256 біт ентропії);
- «одне активне посилання на користувача» вирішується однією мапою `user_id -> хеш`;
- відповідь на запит має бути однаковою *за змістом* і за формою для відомого й невідомого email; у реальному сервісі ще й за часом, тому відправку листа виносять у фонову чергу;
- слабкий пароль не має «спалювати» токен, а невідомий токен не має відрізнятись від простроченого.

**Подумай:**
- `secrets.token_urlsafe(32)` замість `random` та UUID1; порівняння секретів `hmac.compare_digest`;
- обмеж частоту запитів на email і IP (завдання №53), інакше це канал для спаму на чужу пошту;
- після зміни пароля завершуй усі активні сесії користувача (завдання №160) і повідомляй його листом;
- токен у URL потрапляє в логи й `Referer`: чому посилання краще вести на сторінку, що одразу «обмінює» токен, і додати `Referrer-Policy: no-referrer`.

**Перевірка:** `python check.py t166`. Лише стандартна бібліотека.
