# №213 · Делеговані права агента 🔴

**Ситуація.** Користувач просить AI-агента «розбери мою пошту й постав зустріч». Найпростіше віддати агентові токен користувача, і саме так роблять у прототипах. Тоді одна prompt injection у листі дає зловмиснику всі права користувача на всі служби (CWE-269, CWE-863, excessive agency з OWASP LLM Top 10). Правильно: агент обмінює токен користувача (token exchange, RFC 8693) на новий, вужчий за правами, короткоживучий, прив'язаний до одного ресурсу й з записом, хто саме діє.

**Що зробити** у `solution.py` (точні правила в докстрингу; клас `ExchangeError` уже готовий):
- `exchange`: видає новий токен, права якого це перетин прав користувача, задачі та стелі агента; порядок десяти перевірок і коди відмов зафіксовані;
- `authorize`: перевірка токена на боці ресурсу (термін, аудиторія, права);
- `audit_chain`: хронологічний ланцюжок «користувач → агент → субагент» для журналу аудиту.

Криптографії тут немає: токен це `dict`, час передається параметром.

**Підказки (без розв'язку):**
- запитай себе: якщо агент просить більше, ніж дозволено, його запит краще мовчки обрізати чи відхилити, і чому відповідь на це різна для людини й для агента, якого міг обманути чужий текст?
- у токені, виданому агентові A, вже вужчі права. Що гарантує, що субагент B, у якого стеля вища, не отримає більше, ніж мав A?
- вкладений `act` читається ізсередини назовні: де в ньому «перший», а де «поточний» виконавець, і що з цього треба перевіряти на цикл?
- термін життя нового токена не може бути довшим за термін токена, який обмінюють: чому?
- токен для однієї служби не можна обміняти на токен для іншої: яку атаку це закриває (confused deputy)?

**Подумай:**
- де в production живе політика `agents` (реєстр агентів, OPA/Cedar, завдання №235) і хто має право її змінювати?
- RFC 8693 розрізняє impersonation (`sub` = користувач, агент невидимий) і delegation (`act`): чому для агентів майже завжди потрібне друге?
- як відкликати вже видані токени (короткий TTL, introspection, DPoP з №234) і що робити, якщо агент зациклився на обміні?
- звʼязок із №137 (авторизація tool calls) і №238 (workload identity): токен агента це лише перший шар, другий це перевірка кожного виклику інструмента.
