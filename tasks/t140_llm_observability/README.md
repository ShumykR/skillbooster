# №140 · Observability для LLM: трасування, вартість, затримка 🔴 🤖

**Ситуація.** Користувач скаржиться: «чат відповів повільно і дивно». У звичайних логах видно один HTTP-запит на 14 секунд. Але що саме було повільним: пошук у векторній БД, виклик моделі, повторна спроба після 429? Скільки токенів та грошей витрачено? Чи не з'їв цей запит увесь бюджет користувача? Для цього потрібне трасування: trace на запит, span на крок, generation на виклик моделі з токенами, вартістю та часом до першого токена.

**Що зробити** у `solution.py` (структури та правила в докстрингу): `LlmTracer`:
- `trace(...)` і вкладені `span(...)` (контекстні менеджери, стек батьківських span, запис помилок із повторним підняттям винятку);
- `generation(...)` з токенами, вартістю за таблицею цін і `first_token()` для TTFT;
- за замовчуванням **тексти промптів та відповідей не зберігаються** (лише довжини), бо це персональні дані (№138); зберігання вмикається прапорцем;
- `report()`: помилки, p50/p95 затримки, вартість і токени за моделлю та користувачем, найповільніші trace.

**Підказки (без розв'язку):**
- trace завершується в `finally`, щоб запис з'явився й тоді, коли виняток летить далі;
- виняток, який спіймали всередині блоку, позначає span помилкою, але не весь trace;
- вартість невідомої моделі це `None`, а не `0`: так видно, що ціни бракує, а підсумок не вводить в оману;
- перцентилі за nearest-rank рахуй цілочисельно (як у №110).

**Подумай:**
- як це співвідноситься з OpenTelemetry (span, атрибути, trace_id між сервісами, №103) та з Langfuse/Phoenix, які додають ціни, оцінки якості й датасети;
- які атрибути корисні для налагодження (модель, версія промпту, кількість знайдених чанків, причина ретраю) і які не можна писати (тексти, ключі);
- як пов'язати trace з correlation id із логів (№101) та з оцінкою якості від користувача (👍/👎) і eval-прогонами (№131);
- як сповіщати за вартістю й TTFT (SLO для чату: p95 TTFT < 2 с) за аналогією з №104.

**Перевірка:** `python check.py t140`. Лише стандартна бібліотека. Далі: обгорни виклики моделі в capstone цим трасувальником (або підключи Langfuse/OTel-експортер) і подивись розподіл вартості по користувачах.
