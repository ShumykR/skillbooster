# №7 · Єдиний формат помилок (RFC 7807) 🟡

**Ситуація.** Одні ендпоінти повертають `{"detail": "..."}`, інші `{"error": "..."}`, валідація видає масив, а необроблений виняток дає HTML зі стеком і текстом SQL-запиту. Клієнти пишуть п'ять різних парсерів помилок, а зловмисник вчиться на ваших трасуваннях.

**Що зробити** у `install_error_handlers` (контракт у докстрингу): один формат для всіх помилок за [RFC 9457 (раніше 7807)](https://www.rfc-editor.org/rfc/rfc9457.html), безпечний для зовнішнього світу.

**Підказки (без розв'язку):**
- FastAPI-ий `HTTPException` це підклас Starlette-ового; щоб ловити ще й 404/405 від роутера, реєструй обробник для `starlette.exceptions.HTTPException`;
- `app.exception_handler(Exception)` обробляє «все інше», а в тестах такий застосунок запускають із `raise_server_exceptions=False`;
- `JSONResponse(..., media_type="application/problem+json")`;
- стандартну фразу статусу дає `http.HTTPStatus(code).phrase`.

**Подумай:** помилку треба ще й залогувати з `request_id` (це завдання про відповідь клієнту, логування в №101); для 5xx клієнту потрібен лише ідентифікатор для підтримки, а не деталі.

**Перевірка:** `python check.py t07` (потрібні `fastapi` і `httpx`, вони в `requirements.txt`).
